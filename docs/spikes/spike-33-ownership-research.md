# Spike 33 Research: How mature systems declare resource-type ownership / containment

**Status:** Research only — **point-in-time survey (2026-08-18), retained as reference, not as current-state.** Spike 33 shipped 2026-08-24 taking recommendation **R1 (option b)**: one shared Go declaration in `internal/configitems/registry.go`. Two things below are now historical: `internal/graphdiff/rollup.go` **no longer exists** (the diff preview's owned-child rollup was removed 2026-08-24 — owner was never a decided requirement there), so the audit collector is the single consumer; and the "three copies" problem is fixed. Current state: `docs/reference/DGRAPH.md` § "ConfigItem ownership". The comparative evidence below (NetBox / ServiceNow / Backstage / K8s / Terraform / Crossplane / Helm) is what retains value.
**Author:** background research session (Opus).
**Date:** 2026-08-18.
**Scope:** orbital only. Informs the mechanism choice for consolidating ConfigItem ownership type-policy.
**Relates to:** ROADMAP Spike 33; `docs/reference/DGRAPH.md` § "ConfigItem ownership (owned-child model)".

## 0. The orbital question, restated

Ownership *instances* already live in DGraph as the child→owner edge (settled, correct). The *type-policy* — "which edge **types** are containment, and their precedence" — is currently encoded **three** times, and the copies can drift:

1. `internal/graphdiff/rollup.go` — `ownerEdges []string` (explicit, ordered, most-specific-first; precedence is list order). Drives the export diff-preview tree.
2. `internal/handler/server.go` `collectRelatedOrbIDs` + `internal/handler/cluster.go` `collectClusterRelatedOrbIDs` — ownership encoded **implicitly** in the hand-written traversal order over the query-response struct. Drives audit-event rollup under the owner.
3. `internal/configitems/registry.go` — the `Type` struct **already** carries `OwnerType`, `OwnerField`, `ChildField`. This registry is the single source for the audit before-fetch pipeline, the JS editor subtree paths, and the delete-cascade; its package doc says it exists precisely to kill a *"~13 places"* drift problem, and five handlers import it. **`ownerEdges` and `collect*` do not import it.**

Spike 33's open question: consolidate onto one source — **(a)** an ownership annotation on the owner-field in `schema.graphql` parsed by orbital's schema-loader, or **(b)** one shared Go declaration both consumers import. This report gathers how comparable systems answer the same question.

Two orbital facts constrain the answer up front:

- **DGraph rejects unknown schema directives.** DGraph's GraphQL supports a fixed set of 19 directives (`@auth @cascade @custom @deprecated @dgraph @embedding @generate @hasInverse @id @include @lambda @remote @remoteResponse @search @secret @skip @withSubscription @lambdaOnMutate`, plus `@default`) and provides **no mechanism to define a new user-named directive** such as `@owns` ([schema directives](https://docs.dgraph.io/graphql/schema/directives/)). The built-in `@custom` directive ([custom-resolver docs](https://docs.dgraph.io/graphql/custom/directive/)) is **not** a counterexample — it attaches a custom *resolver* (external HTTP / remote GraphQL calls), not static metadata, so it cannot carry an ownership tag a loader would read. A schema carrying an unrecognized directive is rejected in `postGQLValidation`; the request to "ignore unsupported directive" rather than error was filed as a bug and the expected-but-not-actual behavior was a clean update ([dgraph #4799](https://github.com/dgraph-io/dgraph/issues/4799)). **An inline `@owns` directive therefore cannot be part of the schema uploaded to `/admin/schema`.** Option (a) must instead be a **comment convention** DGraph never parses, or a **strip-before-upload** step on orbital's own copy of the file. *(Correction 2026-08-24: an earlier draft wrote "no custom type-system directive," which was ambiguous given the built-in `@custom`; the accurate claim is that no **user-defined** directive is possible — `@custom` is a resolver mechanism. Conclusion unchanged.)*
- **Orbital does not parse `schema.graphql` today.** It reads it as bytes and uploads it; the mutation-guard in `graphql.go` deliberately uses a regex, not `vektah/gqlparser`, explicitly to avoid the parser dependency. Option (a) adds orbital's first schema-parsing code path (a comment scanner or a new AST dependency + a strip step).

## 2. Compact per-system evidence (cited)

### NetBox — ownership is a compile-time property of the type
- Cross-type containment (Site→Location→Rack→Device→Interface) is plain `ForeignKey` fields declared **on the lower object**; self-nesting trees (Region, Location) use `TreeForeignKey(to='self')` via `NestedGroupModel` (django-mptt). Source: [`netbox/models/__init__.py`](https://github.com/netbox-community/netbox/blob/main/netbox/netbox/models/__init__.py), [`dcim/models/device_components.py`](https://github.com/netbox-community/netbox/blob/main/netbox/dcim/models/device_components.py).
- **Drift guard #1 — inheritance-predicate registry.** Capabilities are opt-in mixins (`ChangeLoggingMixin`, `JournalingMixin`, …); `register_model_feature('change_logging', lambda m: issubclass(m, ChangeLoggingMixin))` populates a live predicate map, so a new model that inherits the mixin **auto-enrolls** — no hand-maintained list ([`features.py`](https://github.com/netbox-community/netbox/blob/main/netbox/netbox/models/features.py)).
- **Drift guard #2 — `NotImplementedError`.** Device components must implement `parent_object`; the base raises if you forget — a build-time guard against a new type silently lacking its parent.
- **Multi-edge, single canonical parent.** An Interface has three distinct self-FKs (`parent`/`bridge`/`lag`) — separate named edges, so nothing is inferred; the canonical containment parent for rollup is always `parent_object → self.device`.
- **Child-change rollup precedent.** `ObjectChange.related_object` is a GenericFK; components override `to_objectchange()` to set `related_object = self.device`, so an interface edit surfaces in the **device's** changelog — a direct analog of orbital's Server→iDRAC audit aggregation. `request_id` (UUID) correlates all records from one request. Source: [`core/models/change_logging.py`](https://github.com/netbox-community/netbox/blob/main/netbox/core/models/change_logging.py), [Change Logging docs](https://netboxlabs.com/docs/netbox/features/change-logging/).

### ServiceNow CMDB — ownership as runtime data (the cautionary case)
- Relationships are rows: `cmdb_rel_ci{parent, child, type→cmdb_rel_type}`; the type record carries directional `parent_descriptor`/`child_descriptor` (`Contains::Contained by`, `Depends on::Used by`). Containment is just one type among many, distinguished only by descriptors ([ServiceNow Guru — walking the relationship tree](https://servicenowguru.com/cmdb/walking-servicenowcom-cmdb-relationship-tree/), [community: CI relationships](https://www.servicenow.com/community/in-other-news/diving-into-ci-relationships/ba-p/2272684)).
- Which types *may* contain which lives in `cmdb_rel_type_suggest` (Suggested Relationships) — **advisory only**; it populates the editor's suggestions but does not block an off-model edge ([community KB](https://www.servicenow.com/community/cmdb-forum/how-to-read-the-suggested-relationships-in-servicenow/m-p/2835652)).
- Because the type-policy is admin-edited data with no build step, a new CI class introduces drift caught only by **CMDB governance**, not code review. The one place relationship type feeds logic is **dependent relationships** consumed by the IRE, where "a dependent CI can have only a single parent with dependency" — a data-level canonical-parent rule ([IRE fundamentals](https://www.servicenow.com/community/itom-forum/what-is-dependent-identification-rule-and-how-it-will-work/m-p/930556)).
- Dependency Views render a tree by choosing a **root** and walking `cmdb_rel_ci` ±3 levels; cycle safety is a traversal-time visited-set + depth cap, not schema-enforced ([Dependency Views docs](https://www.servicenow.com/docs/r/servicenow-platform/dependency-views/c_NextGenBSMMaps.html)).

### Backstage — one declaration emits both directions
- Spec fields (`spec.owner`, `subcomponentOf`, `system`, `parent`/`children`, `dependsOn`, `providesApis`…) are **not** the relations; `BuiltinKindsEntityProcessor.postProcessEntity` synthesizes them, and every mapping goes through one helper `doEmit(targets, ctx, outgoingRelation, incomingRelation)` that emits **both directions at once** — so the outgoing/incoming pair can never drift ([BuiltinKindsEntityProcessor.ts](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/processors/BuiltinKindsEntityProcessor.ts), [well-known relations](https://backstage.io/docs/features/software-catalog/well-known-relations/)).
- Containment Component→System→Domain is all the **same** `partOf`/`hasPart` relation; the endpoint *kind* distinguishes levels, not the relation name.
- A **new kind** needs its own `CatalogProcessor` (`validateEntityKind` + `postProcessEntity`) — the mapping then lives with that processor, not centrally: the real drift surface ([extending the model](https://backstage.io/docs/features/software-catalog/extending-the-model/)).
- Graph→tree: no canonical parent. `useEntityRelationGraph.ts` does BFS outward from the **viewed** entity (`rootEntityRefs`), guarded by a `processedEntityRefs` visited-set and `maxDepth`; multi-parent is just multiple incoming edges in a dagre DAG ([useEntityRelationGraph.ts](https://github.com/backstage/backstage/blob/master/plugins/catalog-graph/src/components/EntityRelationsGraph/useEntityRelationGraph.ts)).

### Kubernetes — self-describing instance + code-declared type-policy
- `metadata.ownerReferences[]` lives on the **child**, pointing up (`apiVersion, kind, name, uid, controller *bool, blockOwnerDeletion *bool`). Direction is child→owner ([owners-dependents](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/), [OwnerReference struct](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go)).
- **Canonical parent = the single `controller:true` owner.** Multi-owner is legal but only one controller; `controllerutil.SetControllerReference` returns `alreadyOwnedError` on a conflicting second controller ([controllerutil.go](https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/controller/controllerutil/controllerutil.go)).
- **Type-policy lives in controller Go**, in two places that must agree: `.Owns(&appsv1.ReplicaSet{})` on the builder (watch/reconcile wiring) and `SetControllerReference` at child creation (stamps the ref). No central registry ([builder/controller.go](https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/builder/controller.go)).
- **Cross-namespace ownership is disallowed by design**; a namespaced owner must be same-namespace (a namespaced child may have a cluster-scoped owner). GC (foreground/background/orphan) is the only DAG walker ([garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/)).

### Terraform / Crossplane / Helm — three points on the spectrum
- **Terraform:** containment is the module tree in the resource **address** (`module.foo["a"].aws_instance.bar[0]`), single-parent; the dependency **DAG** (implicit refs + `depends_on`) is a *separate* many-to-many structure that **hard-errors on cycles** ("no cycles and a single root"). Plan output is flat actions (`+ - ~ -/+`) keyed by address; nesting is only the module path ([resource addressing](https://developer.hashicorp.com/terraform/cli/state/resource-addressing), [graph internals](https://developer.hashicorp.com/terraform/internals/graph)).
- **Crossplane:** cleanest split — **type-policy** in a version-controlled `Composition` (which composed types make up an XR) vs **instance ownership** as K8s `ownerReferences` + `resourceRefs` on live objects; `crossplane beta trace` renders the tree from those refs ([compositions](https://docs.crossplane.io/latest/composition/compositions/), [composite resources](https://docs.crossplane.io/latest/composition/composite-resources/)).
- **Helm:** weakest — ownership is a **label/annotation convention** plus the release Secret's manifest list; no ownerReferences, no in-cluster hierarchy, delete iterates the manifest ([Helm advanced](https://helm.sh/docs/topics/advanced/), [managed-by adoption PR #7649](https://github.com/helm/helm/pull/7649)).

## 3. Synthesis — what the evidence says about (a) vs (b)

**The dominant pattern is: type-policy lives in version-controlled code; instance-ownership lives on the instance.** Six of seven comparables keep the *type-level* "which type owns which" as code or code-adjacent config — NetBox (FK fields), Kubernetes (`.Owns()`), controller-runtime, Terraform (HCL), Crossplane (`Composition`), Backstage (a processor). The **only** system that keeps type-policy as runtime, admin-editable **data** is ServiceNow — and it pays with exactly the failure orbital's settled constraint already forbids: no build step validates it, correctness becomes a governance problem, and nothing fails when someone forgets to wire a new class. This is a strong, independent confirmation of orbital's "NOT Postgres" decision — and it applies with equal force to any runtime-configurable ownership.

**On (a) schema-annotation vs (b) shared Go declaration**, the comparables split by *what their schema is made of*:

- NetBox's ideal — "ownership lives literally on the field, next to the schema" — is achievable there **only because NetBox's schema is code** (a Django model field is simultaneously the schema declaration and the Go/Python ownership declaration). Orbital's `schema.graphql` is a *separate artifact* from its Go. So NetBox does not actually favor (a) over (b) for orbital; it favors "declare it where the schema is declared," and for orbital the two are different files.
- Backstage is the sharpest lesson for (b): **one `doEmit` call emits both directions**, so the two consumers (forward and inverse relation) provably cannot drift. Orbital's target is identical — one entry should yield both the diff rollup's owner-edge *and* the audit `collect*` traversal.
- Kubernetes/Crossplane show the **canonical-parent mechanism orbital needs**: among possibly many owners, exactly one is `controller:true`. Orbital's `ownerEdges` precedence (NIC → adapter before server before device) is the same idea expressed as list order; IPAddress (four owner edges) is orbital's live multi-parent case.

**Weighing (a) for orbital specifically:** its theoretical win is co-location/reviewability — the ownership change and the schema change appear in one diff. But that win is undercut twice: (1) **DGraph rejects unknown directives**, so a real `@owns` directive can't ship in the uploaded schema — it must be a **comment** (unvalidated by any GraphQL tool) or a directive that orbital **strips before upload** (extra pipeline step); (2) orbital has **no schema parser today** and deliberately avoids `gqlparser`, so (a) introduces the first parse path. A comment convention gets co-location but loses the one thing that makes co-location valuable — machine validation — because no tool understands `# @owns`.

**Weighing (b) for orbital specifically:** the shared Go declaration **already exists** — `internal/configitems/registry.go` has `OwnerType`/`OwnerField`/`ChildField`, is imported by five handlers, and was created expressly to defeat a 13-place drift problem. Choosing (b) is therefore **finishing an existing consolidation, not starting a new one**: point `graphdiff.ownerEdges` and the audit `collect*` at the registry. Cost is low (no parser, no dependency, compiler-checked), deploy-atomicity is perfect (compiled in). Its one residual drift surface — the Go table vs `schema.graphql` — is closable by a test (below), which hands back (a)'s drift-catch benefit without (a)'s parser cost.

| Criterion | (a) schema annotation | (b) shared Go declaration (extend registry) |
|---|---|---|
| Drift vs the schema | Best *in principle* (same file) — but a comment is unvalidated; a directive is rejected by DGraph | Good; residual Go↔schema gap closed by a consistency test |
| Drift across consumers | Depends on a new loader all consumers call | Solved — one table, compiler-enforced, both import it |
| Reviewability | One diff — if it's a directive (which DGraph won't accept); comments are easy to typo | Two in-repo files, co-reviewed; `add-configitem.md` already lists both |
| Deploy-atomicity | Ships with schema, but needs strip-before-upload for a directive | Perfect — compiled into the binary |
| Tooling cost | High — orbital's first schema parser (comment scanner or `gqlparser` + strip) | Low — extends a package five files already import |
| Precedent weight | NetBox-*style* only if schema==code (not orbital's case) | Kubernetes, Crossplane, Backstage, Terraform, NetBox-internals |

## 4. Recommendations

**R1 — Choose (b): make `internal/configitems/registry.go` the single source, and derive both consumers from it.** The registry already models ownership, already beat the same drift class once, and needs no parser or dependency. Have `graphdiff.ownerEdges` and the audit `collect*` build from the registry rather than hand-maintaining parallel truth. This matches the weight of the evidence (type-policy as version-controlled code) and orbital's own settled "not Postgres / declare it once" reasoning, and it treats (a)'s only realistic orbital form — an unvalidated schema comment — as strictly worse than a compiler-checked Go table. *(Do not pursue an inline `@owns` directive: DGraph rejects unknown directives — [dgraph #4799](https://github.com/dgraph-io/dgraph/issues/4799), [directives docs](https://docs.dgraph.io/graphql/schema/directives/).)*

**R2 — Model the canonical parent explicitly and order-sensitively, mirroring Kubernetes' single `controller:true`.** The registry today records one `OwnerType` per type, but the diff rollup needs, for multi-parent types, **an ordered list of candidate owner edges with a declared precedence** (orbital's live case: `IPAddress` has four owner edges; `NetworkInterface` must nest under adapter before server before device). Extend the registry entry to carry ordered owner edges (or a priority) so precedence is data, not the accident of a Go map's iteration order — and so "exactly one presentation parent wins" is explicit, as it is for K8s (`SetControllerReference` errors on a second controller) and NetBox (`parent_object` is a fixed single value). Keep this as *presentation* precedence only — per the ROADMAP non-goal, it is not operator-tunable.

**R3 — Add a schema-consistency test to recover (a)'s co-location benefit without a runtime parser.** Mirror NetBox's build-time `NotImplementedError` guard and Backstage's single-emit invariant with a Go test that parses `schema.graphql` **in the test only** (not at runtime) and asserts every registry `OwnerField`/`ChildField` corresponds to a real `@hasInverse` edge, and that every ConfigItem type in the schema has a registry entry. This catches the one drift (b) can't — someone renaming a schema edge without updating the registry — at `make test-unit` time, and keeps the runtime free of a parser dependency. Update `docs/playbooks/add-configitem.md` to point at the single declaration.

### Risks and edge-cases the comparables surface

- **Multi-parent (real today): `IPAddress`.** Every graph system that renders a tree picks **one** parent — K8s `controller:true`, NetBox `parent_object`, Terraform's single module. Orbital must keep declaring one canonical presentation parent by precedence; do not attempt to render a node under all its owners.
- **Cycles — orbital's `Rollup` is not cycle-safe.** If ownership data ever forms a loop (A.owner=B, B.owner=A), `link()` builds a Change tree where each is the other's child, and `sortChildren`/`computeDescendants` recurse infinitely. Every comparable guards this: NetBox `clean()` rejects self-or-descendant, Terraform hard-errors, Backstage/ServiceNow use a visited-set. Recommend a visited-set/precedence guard in `Rollup` (and/or the R3 test asserting the owner graph is acyclic). Physical containment shouldn't cycle, but nothing currently prevents it.
- **Precedence is load-bearing and must stay deterministic.** `ownerEdges` correctness depends on list order (most-specific-first). Any registry-derived edge list must preserve an explicit order — a map won't do (Go map iteration is randomized).
- **Cross-namespace ownership.** Kubernetes forbids it by design. Orbital should state explicitly whether an owned child may live in a different namespace than its owner (recommend: no — containment implies same namespace) and, ideally, assert it in the R3 test.
- **New-kind drift moves, it doesn't vanish (Backstage).** Even with one central declaration, a *new* type still needs its registry entry; the mitigation is the R3 consistency test failing the build, not trusting a checklist.
- **DGraph `@hasInverse` is only a hint, not the policy.** It's bidirectional and encodes neither direction-of-ownership nor precedence — which is exactly why ownership must be declared out-of-band. The registry's `OwnerField` already names the specific `@hasInverse` pointer, giving R3 a concrete thing to cross-check.
