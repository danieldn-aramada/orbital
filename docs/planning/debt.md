# Known debt

Tracked technical debt for orbital. Split out of `ROADMAP.md` on 2026-08-28 — it had grown to 42 entries (one of them 2.5 KB), which buried the milestone view that ROADMAP exists to give.

**This is an interim home.** By the convention of every comparable project (Kubernetes, Rust, Django, Terraform), debt belongs in the issue tracker with labels, not in a file. Move it there when the workflow is ready; until then, this file keeps it out of the roadmap.

Entries are grouped by whether they need design input before someone can pick them up.

**Every entry here is OPEN.** A closed item is **deleted**, not struck through — `CHANGELOG.md` records what shipped and git history holds the deliberation, so a struck row is a second record of the same thing and they drift (the same reasoning that removed ROADMAP's "recently shipped" section). *Nine struck-through rows were removed 2026-09-14 after each was re-verified as genuinely done in code.*

⚠️ **Before deleting a row, read it for work it still carries.** Three of those nine had an open follow-up written *inside* a row marked DONE — a missing test, a missing e2e, a lesson not recorded in any domain doc — and deleting them blind would have dropped all three. Promote what survives, then delete.

The correct orbId shape lives in code, so the registry is no longer the single source of truth for orbId. **Why it bites:** for an *optional* child (first-time-create is the common case) the wrongly-derived id is what actually gets written — a silent correctness footgun, not cosmetic. **Fix:** let the `Type` struct declare its orbId pattern so `BuildEditTargets` derives the right id with no override. **Design decision (why Track B):** the pattern needs natural-key inputs the registry doesn't hold (owner serial/serviceTag, FQDD, …). Options: **(a)** `OrbIDKey func(parent map[string]any) string` per-type closure — handlers pass the fetched parent object; handles multi-part keys (network types); **(b)** declarative template + `KeyField` naming the parent field that supplies the key (e.g. `server-maintenance-{key}`, KeyField `serviceTag`) — simpler but weak for multi-part keys; **(c)** just move each construction into a named registry helper (declared once, not re-derived per handler). Recommend (a). **Scope:** `registry.go` (`Type` + `BuildEditTargets`, retire `leafSuffix`); remove the now-redundant `OverrideEditTargetOrbID` calls in `server.go` (+ audit `cluster.go` / any network editor) where the pattern covers them, keeping override only for genuine legacy/fetched-id cases; add a registry test asserting each editor-creatable type derives its documented `DGRAPH.md` orbId. **Acceptance:** adding a new prefix-convention ConfigItem needs ZERO handler orbId override — schema + registry entry is enough (the add-configitem playbook's promise). Pin with a test that derives `ServerMaintenance` → `<ns>:server-maintenance-<serial>` with no handler code. |
| **The cascade delete is not a compare-and-swap, and never checks a child's version** | **Promoted 2026-09-14 out of the change-request CAS row in `backlog.md`, which was struck as DONE with this named inside it as "still open, separately".** The CAS fix works by injecting `version: { eq: $version }` into a GraphQL mutation's own filter so DGraph evaluates it as part of the write. `DELETE /api/v1/config-items/:type/:id` has no such filter to rewrite: it plans the cascade and writes through DQL `/mutate?commitNow=true` (`delete.go:832`). So `?version=` there is a **read-then-write TOCTOU**, not a CAS — `checkDeleteVersion` (`delete.go:973`) runs `queryConfigItem(... first: 1) { version }`, compares in Go, and the delete proceeds unguarded. **And it reads the ROOT only**, while the cascade removes children whose versions are never looked at — so an edit to an owned child in the gap is destroyed with no conflict. **Why Track B:** there is no filter to rewrite, so the remedy is a design call — a DQL-level `@if` conditional upsert covering every planned uid, or planning the cascade inside one txn that re-reads versions before committing. **Acceptance:** a delete whose root moved between plan and write is refused, not applied; a delete whose CHILD moved is likewise refused; the refusal is `MVCC_CONFLICT`, matching the `/graphql` path. |

### Architecture — requires design discussion before any code

| Item | Notes |
|---|---|
| Orbital HA — pervasive single-replica assumptions | Deployed `replicas: 1`, `strategy: Recreate`. Divergence ingester (`lastIngestedByDC` in-memory), backup scheduler (cron double-fires), publish-history ingester all assume single-leader. Going HA needs leader election / advisory locks / dedicated ingest deployment. **Do NOT scale past `replicas: 1`** — double-ingestion corrupts divergence state. |
| The graphdiff-rendering surfaces build HTML in JavaScript, not Go templates | **Raised 2026-09-01.** The house pattern is a Go template plus `HX-Request` fragment negotiation inside the existing handler — `audit.go`, `backup.go`, `export.go`, `datacenter.go`, `cluster.go`, `networkdevice.go`, restore-jobs, oci-artifacts and divergence-reports all do it. **Five surfaces do not:** the change-request queue, the change-request review page, export preview, artifact compare, and approval-policies. `grep -n "HX-Request" internal/handler/changerequest*.go` returns nothing — those endpoints are JSON-only with no fragment representation. **This is ONE decision, not five.** The four diff-adjacent surfaces share `renderExportPreviewTable` (three callers: `orbital.js:638` export preview, `:2886` change-request diff, `:3964` artifact compare), all consuming the identical flat `changes[]` a single graphdiff core produces. Server-rendering any one of them needs a Go twin of that renderer or the three drift, so the real question is **"should the graphdiff renderer live in Go"** — answer it once and all four convert together. Do NOT convert a single page, and especially not part of one: splitting a page across both patterns is worse than either. **The framing that made this look principled was wrong.** "API-first — orbital's UI is a consumer of its own API, never a privileged server-rendered path" was read as forbidding server-rendered HTML. It does not: CLAUDE.md's own rule is to branch on `HX-Request` **inside the existing handler**, so the JSON contract is untouched and the fragment is a second representation of the same resource. The two conventions never conflicted. **Two concrete costs, both stronger than the consistency argument.** (1) *The client interprets an authorization decision* — `availableActions` is derived server-side from role, authorship, status and prior approvals, and `actionButtons()` in `orbital.js` loops over it to decide which controls exist. It is faithful today and nothing enforces that it stays so; a fragment makes drift structurally impossible. (2) *Escaping is manual* — every interpolation needs an explicit `esc()`, where a Go template escapes by construction. All current call sites are correct, but titles, descriptions and review comments are now free-form user text flowing through string concatenation. **No user-visible payoff**, which is why it is filed rather than done. |
| Storage and Network panels cannot surface a proposed change at all | **Raised 2026-09-02.** The proposed-change surfaces (banner, field marks, tab dots) all key on `data-field-orbid` + `data-field="<name>"` rows, which only exist on **field/value tables** — Server Summary, iDRAC, Maintenance. Storage and Network panels render **lists of child entities** (a row per device: Name / Manufacturer / Capacity / Serial / WWN), so a change request touching a `StorageDevice` or `NetworkInterface` field shows **nothing anywhere on the server tab** — no mark, no dot, and the top-of-tab banner only counts requests without saying where. A reviewer can therefore retype exactly the edit this feature exists to prevent. **Design call:** mark at ROW level ("this device has a proposal", linking to the request) which needs a per-row orbId and a different mark shape than the field tables use; or tab-dot only, so the tab at least says "look in here" without per-row detail. Lean row-level — a list of 24 storage devices with an undifferentiated tab dot is barely better than nothing. Do NOT bolt `data-field` rows onto a list table to reuse the existing renderer: the field tables are field-per-row and these are entity-per-row, and forcing one shape onto both is how the three tables that "must not drift" start drifting. |
| A changeset cannot distinguish ASSERTED intent from INCIDENTAL fields | **Raised 2026-09-02.** `set` is target end-state, so `set: {a: 1, b: 2}` where `b` was already `2` is indistinguishable from a deliberate assertion of both — the reviewer cannot tell narrow intent from wide. Mitigated for *display* by `fields[]` on `GET /{id}/diff` — one row per written field resolved to an `outcome` of `applies` / `satisfied` / `conflict`, computed by the same classifier the merge uses (`changerequest_api.go:480-492`, which supersedes walking `changes` and `satisfied` separately; *entry updated 2026-09-14, it previously cited `satisfied[]`*). The mitigation still depends on `base_values`: a request whose snapshot read failed, or one created before the ancestor existed, degrades silently to "everything looks proposed" with no marker saying the comparison was unavailable. **Two candidate fixes:** carry an explicit `asserted` flag per field (honest, but a new API concept and every client must set it), or surface `baseValuesAvailable: false` on the diff response so a client can say *"cannot distinguish"* instead of implying it did. Lean the second — it is one boolean and it removes a silent failure rather than adding a concept. Related: `CHANGE-CONTROL.md` § How we arrived at this shape. |
| Auto-apply DGraph GraphQL schema on startup | Today orbital does NOT apply `schema.graphql` on boot, so a schema-bumping image deploy silently drifts until someone POSTs to `/admin/schema` — the 2026-07-27 AKS burn (v0.0.25 queried `retentionDays`, DGraph still v3 → every cluster 404'd). **Proposed:** apply the schema additively on startup, mirroring ent auto-migrate for PostgreSQL. **Design points:** (1) re-scopes the "schema migration out of MVP" decision; (2) blue-green apply to active/blue on boot; (3) additive-only guard; (4) confirm multi-replica racing is harmless (DGraph serializes); (5) fix the `schema.graphql:6` vs `DGRAPH.md` doc contradiction. Alternatives: kustomize initContainer, GitOps PreSync Job. Triggered by the 2026-07-27 burn. |
