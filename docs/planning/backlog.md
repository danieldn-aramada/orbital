## Spikes — open questions

Each spike is a question to answer; results refine MVP/post-MVP scope.

**One audit event per entity, correlated by request id** · *Design done, not started*
Should an audit event describe one entity instead of a whole request, so the per-node changelog is complete? **Verdict: yes.** Design in `docs/spikes/spike-audit-event-per-entity.md`.
> **The gap:** `GET /api/v1/audit-log?orbId=` is orbital's per-node changelog and the API behind every ConfigItem audit tab, but `changes` is **absent for creates** (`computeChanges` intersects `before`'s keys with `after`, and a create has no `before` — so adding a server or seeding leaves a row with no field detail) and **absent for multi-entity events**, which could not be attributed anyway since entries carry no `orbId` while one event may reference N resources. The data survives in `details.variables`, so clients must parse a raw payload for exactly the cases the normalised array exists to spare them — the API-first failure. **Shape: one event per entity + a `request_id`, which is NetBox's model** (one `ObjectChange` per object, correlated by a request UUID); `changes` then becomes single-entity *by construction* and `?orbId=` becomes exact rather than "this event touched, among others, your node". Rejected the cheaper waypoint (keep one event per request, add `orbId` to each change entry) — it fixes the symptom and leaves the root. **The enabler is that the new shape is a SPECIAL CASE of the old:** `audit_event → resources` is already 1:N, so an event with one resource is already legal — **no data migration**, historical rows keep rendering, and this is therefore NOT blocked on Spike 27 (Atlas), which matters because ent auto-migration can add a column but cannot split rows. **Creates are the cheap, high-value half** (no before-state to fetch by definition — emit `before: null` per field, mirroring NetBox's `prechange_data: null`); **multi-op UPDATES are the expensive half** (an N-entity before-fetch on the write path) and are scoped OUT pending evidence a real client sends them — orbital's own paths do not, since the config editor dispatches one request per entity and merge applies items one at a time. **Extend `computeChanges`, never add a second diff implementation** (`AUDIT.md`) — the HTML renderer is pure over it, which is why API and panel cannot disagree. **Non-goals:** a per-field history table (the named antipattern), and backfilling historical events.

**Advisory enforcement for approval policies** · *Not started*
Should an approval policy have a middle state — evaluate and record, but do not block — so a new policy can be rolled out without risking a lockout?
> **Every comparable engine has one and orbital does not:** Kyverno `Audit`, Gatekeeper `dryrun`, HCP Sentinel `advisory`, GitHub rulesets `Evaluate`. Orbital's policies are **Active | Disabled** only (deliberately, 2026-08-30 — two states first, simplest thing that works). **The gap it leaves:** there is no safe way to introduce a policy on a busy namespace and see what it *would* have refused before turning it on. **The work is not the third state, it is the recording** — advisory is indistinguishable from disabled unless a would-have-been-blocked write is written somewhere an operator can read it. Kyverno writes a PolicyReport; orbital would write an audit event, which fits the existing `details` jsonb and the `privileged` precedent (`details.wouldHaveBlocked` + the policy's namespace, which identifies it — one policy per namespace). **Then** the UI's segmented control grows a third segment and `CHANGE-CONTROL.md` loses its "no middle state" caveat. **Do not** reintroduce a global enforcement flag to approximate this — enforcement belongs on the policy, which is what the category does and what `TestApprovalPolicy_DisablingStopsGatingAndKeepsTheRow` pins.

**Change-request lifecycle events in the audit log** · *Not started*
Should the change-request lifecycle (create / amend / approve / reject / close / merge) emit `audit_events`, so a namespace's review history is answerable without opening every request one at a time?
> **What is audited today:** the writes a merge produces (every item goes through `DispatchMutation`, so the *effect* lands in the audit log like any mutation — `changerequest_merge.go:246`), approval-policy create/update/delete with `before`/`after`, bypass writes (`details.privileged` + `details.bypassedPolicy`), and authn/authz failures. **What is not: the lifecycle itself.** It lives in the approval tables — `approval_requests.status` + `updated_by`, one `approvals` row per reviewer (with `approved_at_hash`), one `merge_attempts` row per execution — and surfaces only through `GET /api/v1/change-requests/:id`. So *"what happened to colo-3"* is answerable; *"show me every review action in colo last month"* is not. **Per-request is the right primary view and matches the category** — NetBox and GitHub both stop there, GitHub's timeline being per-PR rather than in the org audit log — so this is not self-evidently a bug. **The question that decides it:** must a compliance reviewer reconstruct a namespace's review history without opening each request? If yes, the lifecycle emits `management` events alongside the table rows; the `details` jsonb already fits and the resource id is the namespace, exactly as policy admin does.
> **Settled 2026-09-02 and NOT part of this entry:** a policy refusal (`403 APPROVAL_REQUIRED`) writes no audit row — business-logic refusals and technical failures are app-log only, per `AUDIT.md` § Row admission. An earlier version of this entry called that an inconsistency with `authorizationDenied` and said to fix it regardless; that was wrong. The two criteria are *state changed* and *security event*, and a policy refusal is neither — the caller has the role, the workflow says "not yet".
> **Two gaps that remain even if the lifecycle stays out of the audit log:** (1) **amend leaves no trace of what it replaced** — `SetPayload` overwrites and `updated_by`/`updated_at` are single-slot, so a request amended three times shows only the last actor and the current changeset. Partly mitigated: amend recomputes `base_hash`, which stamps existing approvals stale, so no approval silently survives a payload swap — but *"was this materially changed after Alice reviewed it"* is still unanswerable. (2) **reject and close carry the actor only in `updated_by`** — durable in practice since nothing follows a terminal state, but a slot rather than an event. Both are cheap to close inside the approval tables (an append-only `approval_request_events` child table) without touching `audit_events` at all, which is likely the right first move if either is wanted.
> **If the audit-log half is built, do NOT duplicate state:** the approval tables stay authoritative for status and approval counts; events record transitions only. And share the shape with the advisory-enforcement entry above — both need "a policy decision worth recording", and two sessions inventing two shapes for it is the obvious failure mode.

**Approval on publish — a second action type, `export.publish`** · *Not started*
Should publishing an artifact require approval, and if so, how is it modelled? **Verdict: yes, gated at PUBLISH, not at export.** Design captured in `.local/spike-publish-approval.md`.
> **Why publish is the chokepoint:** once an artifact lands in the OCI registry it is out of anyone's hands — orb *polls* the repo (`ORB.md`, `ORB_ENABLE_OCI_REGISTRY`), so there is no human at the edge deciding to pull, and in an air-gapped site nobody reachable to stop it. Publish is the last gate that exists. It is also the ONLY door: orbital is the sole OCI producer, which gives it the same one-way-through property that makes `writeToDGraph` a real gate rather than a suggestion. **Gating publish also makes the review better**, not just better placed — the artifact already exists and is content-addressed, so a reviewer sees exactly what would ship via `GET /api/v1/export/compare?from=<deployed>&to=<candidate>`. Gating export would mean approving something not yet built. **Shape:** a second `action_type` on the existing engine, NOT a change request — a changeset is meaningless for a publish, but the engine is action-agnostic by design (`action_type` + opaque `payload` + shared lifecycle) and `approval_policy` is already `UNIQUE (action_type, namespace)`, so this is **additive with no schema change**. Namespace ≈ data center, so "publishes to colo need one approval, dev-netbox does not" falls out of the existing policy shape — the GitHub-Environments model with no new concepts. **Payload pins the artifact DIGEST** (plus jobId for traceability), which removes staleness entirely: the thing approved cannot change underneath you, so there is no rebase logic and no "approved an earlier version" state — unlike `config.mutation`, which needs all of it. **Do NOT** model this as a change request, and do NOT gate `POST /api/v1/export` (building and diffing must stay free, or the review has nothing to look at). **Two open questions:** does a publish whose digest is already deployed still need approval (lean yes — *when* you ship is what a maintenance window governs); and if a newer artifact exists at approval time, warn or refuse (lean warn — the approval is the authority, and refusing would stop a slow reviewer approving anything). **Separately and much cheaper:** if the near-term worry is only that any `dev` can publish, that is one line — `POST /api/v1/export` is on the `RequireRole(dev)` group (`server.go:403`) and could be admin-gated today, no engine work. RBAC and maker-checker are two knobs; every comparable product has both (GitHub Environments, Terraform Cloud) or only the first (Argo).

**Spike 26 — Provider-portable identity: id_token as Bearer** · *Not started*
How do we move orbctl + orbital from the AAD-specific "access_token carries identity" pattern to the standards-aligned OIDC "id_token as Bearer" pattern that works across any OIDC provider?
> **Why it matters:** today's pattern only works because AAD v2 embeds identity claims (`name`, `oid`, `preferred_username`, `upn`) into JWT access tokens — a provider-specific convenience, not the OIDC standard. Auth0/Okta include only `sub`; Google issues opaque access tokens. Pointing orbital at any of those breaks identity extraction. **Current state:** `internal/orbauth/auth.go:24` requests `api://.../user_impersonation offline_access` (no `openid`); `internal/auth/bearer.go:84-86` reads `claims.PreferredUsername`→`claims.UPN` (AAD-only); orbctl never sees an id_token. **Target:** orbctl requests `openid email profile offline_access`; persists + sends `id_token` as Bearer; orbital verifies id_token signature + audience + standard claims. Matches the existing UI `/auth/callback` flow (`oidc.go:62`, already uses `gooidc.IDTokenVerifier`) and the kubectl convention. **Scope:** `internal/orbauth/`, `internal/auth/bearer.go`, `internal/orbctl/`; migration path for existing users; decide if access_token is still useful. **Open Q:** does any orbital path actually need the access_token, or is it purely identity-as-claims today? Triggered by 2026-06-24 conversation.

**Spike 27 — Adopt Atlas for Postgres schema migration** · *Design complete, not started*
How does orbital handle schema evolution against legacy data — adding constraints to populated tables — without crashlooping deploys?
> **Design: `docs/spikes/spike-27-atlas-migrations.md`.** **Trigger:** v0.0.23 AKS deploy crashlooped adding an FK on `registry_artifacts.export_job_id`; long-lived DB had orphans that ent's schema-diff can't see. Fresh test DBs miss the class entirely. **Adopt Atlas** (ariga.io, ent-native — already an indirect dep; ent's migration engine *is* Atlas): versioned SQL under `ent/migrate/migrations/`, data migrations interleaved, `atlas migrate lint` in CI. **Decided: free tier only** — `atlas migrate lint` does **not** catch orphan-rows-blocking-an-FK (no analyzer covers it; lint never connects to a DB), so it would not have caught v0.0.23. The verified free equivalent is a hand-written `DO $$ … RAISE EXCEPTION $$` precondition block plus DML-before-DDL in the same migration; convention is that every FK/NOT-NULL-on-populated-table migration carries one. **Also found:** ent auto-migration **cannot rename** — `planInspect` only inspects ent-declared tables, so a renamed-away table silently orphans with all its data (verified in ent v0.14.6 source); and `WithDropColumn(true)` is armed in production at `main.go:67`. **Scope:** replace `db.Schema.Create(...)` in `cmd/orbital`; move migrations off startup (init container / `--migrate` flag) so a failure fails a Job instead of crashlooping every replica; CI applies pending migrations against a redacted snapshot of AKS Postgres; drop `WithDropColumn(true)`; orb SQLite follows later, not concurrently. **Independent of Spike 34** — that rename runs first under auto-migration, so Atlas baselines the already-correct schema. **Deliverable:** a new `docs/reference/MIGRATIONS.md` (decisions inline, per CLAUDE.md's Reference Index — the `docs/decisions/` ADR directory was removed 2026-07-07). Rejected: Liquibase/Flyway (Java tax), custom tooling (same reasoning as the "do not build a custom migration tool" decision for DGraph in CLAUDE.md § Settled Decisions).

**Spike 28 — In-pod bundler → orbital service-auth model** · *Post-MVP*
Should the co-located cb-bundler authenticate to orbital's `/graphql` via full AAD client-credentials (current) or via a loopback/localhost trust — and reconcile the contradictory docs?

**Spike 30 — Pre-export change preview ("diff preview")** · *Shipped 2026-08-24*
As a data center owner, how do I review how the export I'm about to publish differs from the last one I published, instead of publishing blind?
> **Shipped.** Synchronous, read-only `POST /api/v1/export/preview` returning a flat, per-`orbId` **desired-state content diff** — current blue subgraph vs the last published artifact pulled by OCI digest — computed in memory (no scratch DGraph). Surfaced in orbital's UI as the confirm gate on Publish. Explicitly a desired-state delta, **not** an apply-forecast. Rejected the audit log as the diff source (a `dropAll` restore is invisible to it). Shares its normalize+compare core with **Spike 25** (published-vs-published), which should reuse it rather than build an audit engine.
> **Reference (spike doc folded in and deleted per the spike-lifecycle rule in CLAUDE.md):** endpoint semantics, baseline states, why-not-the-audit-log, and precedent → `docs/reference/OCI.md` § "Export preview"; snapshot normalization + DGraph wire-shape gotchas → `docs/reference/DGRAPH.md` § "Comparing two graph snapshots"; the `expectedContentHash` guard → `OCI.md` § "Guarded Apply". Implementation: `internal/graphdiff/`, `internal/handler/export_preview.go`.

**Spike 31 — AEP change-management: guarded Apply + selective revert + attribution** · *Shipped 2026-08-25*
As a data center owner reviewing changes from multiple writers, how do I publish exactly what I reviewed — and discard what I don't want?
> **Shipped — orbital's side is complete; the remaining pieces need no orbital code.** (1) **Guarded Apply** built: optional `expectedContentHash` on `POST /api/v1/export` → `409 MVCC_CONFLICT` if intent moved between preview and Apply, with the verified snapshot pinned into the export so *shipped == reviewed*. (2) **Selective revert** is a client pattern, not an endpoint — the preview returns each field's prior value, so revert = writing it back via the existing `update{Type}` mutation. A batch `POST /api/v1/export/revert` was designed and **rejected**: its only gain was atomicity, and partial revert is harmless (nothing shipped; re-preview shows what remains) while the hash guard already ensures you publish what you reviewed. (3) **Attribution** is a client-side join of the diff against `GET /api/v1/audit-log?orbId=…` — diff answers *what*, audit answers *who/when*. **Orbital does not model PIM** — it enforces `RequireRole` on whatever the token carries; elevation is IdP-side. Reference: `OCI.md` §§ "Export preview" / "Guarded Apply", `AUDIT.md` § Event model, `AUTH.md` (PIM boundary).

**Spike 35 — Audit before/after capture, undo, and an intent change feed** · *Not started*
Should orbital persist a full before/after snapshot per changed node — and does that unlock undo-a-change and a CDC-style intent feed?
> **Split out of Spike 34 (closed 2026-08-26) as the part that is still an open design question, not settled work.** Today `details.before` is persisted but `after` is the mutation *input*, and `BeforeFields` is a hand-declared per-type subset. **Verified constraints:** DGraph v25 is Apache-2.0 with **no community/enterprise split** — CDC *is* available to us (`ee_features: ['backup_restore','cdc']`) but is **new-values-only**, so it cannot supply a before-image; there are **no pre-mutation triggers** (lambda pre-hooks were proposed and rejected upstream on latency grounds) and `@lambdaOnMutate` fires post-commit with the client's input, not prior state. The **only** race-free primitive is a **DQL upsert block** (query+mutation in one transaction) — which routes capture through `/mutate`, bypassing the GraphQL proxy that is currently the mutation chokepoint. That tension is the core design question. **Scope:** where to capture; `AuditEventResource` before/after columns (additive, not blocked on Spike 27); changed-fields vs full snapshots (NetBox stores full object snapshots, we lean changed-fields); undo-a-change with an optimistic "changed since" check — **name it distinctly from Spike 31's baseline-anchored publish revert**; blind-spot reduction by snapshot-diffing orbital's own restore/import via `graphdiff`. **Do NOT build the change feed without a named consumer.** If built: REST cursor feed, not Kafka — air-gap-friendly and `GET /api/v1/audit-log` already has `since` + pagination.

**Spike 34 — Audit log: convention, direction, and backlog** · *Closed 2026-08-26*
> **Answered and folded into `docs/reference/AUDIT.md`; spike doc deleted per the spike-lifecycle rule.** The audit log is **provenance for control-plane actions** — every attempt to act on orbital's API, successful or not. It answers *who did what, in one act, and when* (per-event, attributed); it never answers *what is the state* or *what is the net difference* — those are the Topology API and `graphdiff`. Same split AWS makes between Config and CloudTrail. **Convention: CloudTrail primary** for structure/taxonomy, NetBox for per-object presentation, K8s for the two-stream separation. **Shipped:** `events` → **`audit_events`** rename (tables, ent types, handler, file) so both layers share the root noun — the argument is collision, not consistency: K8s minted `audit.k8s.io` precisely because bare `Event` was already taken by a 1-hour-TTL operational stream. Also shipped: a `BeforeFields` drift guard, the phantom `/api/v1/events` route removed from the docs, and the publish-history panel relabelled "Audit Log" with explainers so it stops colliding with the content diff's "Changes". **Retention decided: orbital is not prescriptive** — `ORBITAL_AUDIT_RETENTION_DAYS` default `0` = indefinite, adopter sets it; the unratified "≥ 12 months" claim was removed. **Remaining work → Known debt § "Audit log — open backlog"; the still-open design question → Spike 35.**

**Spike 33 — Unify ConfigItem ownership into a single declaration** · *Shipped 2026-08-24*
As orbital adds ConfigItem types, how do we declare owned-child containment once — instead of hand-maintaining drift-prone parallel lists?
> **Shipped.** Mechanism (b) chosen — one shared Go declaration in `internal/configitems/registry.go` — over (a) a `schema.graphql` annotation, because DGraph rejects unknown directives (`@custom` is a resolver, not metadata) and orbital deliberately has no schema parser. `Type.OwnerEdges` models multi-parent, precedence-ordered ownership (`NetworkInterface`, `IPAddress`, `StorageVolume`); `OwnedChildren()`/`OwnedOrbIDSelection()` drive one generic registry-driven audit collector that replaced both hand-walked `collect*RelatedOrbIDs` functions. **Fixed real drift:** storage devices/volumes and switch-side interfaces now roll up in audit tabs; NetworkDevice and DataCenter aggregate children at all. **R3 consistency test** cross-checks the registry against `schema.graphql` at `make test-unit`. The 7-system comparative survey lived in a spike doc, deleted 2026-08-27 per the spike-lifecycle rule; recoverable via `git log docs/spikes/`. **Non-goal:** runtime-configurable ownership.

| Item | Notes |

| Semantic text colours fail WCAG AA on light backgrounds | **Measured 2026-08-31.** Bulma's `has-text-danger` renders `rgb(255,102,133)` and `has-text-info` `rgb(102,209,255)` — roughly **2.5:1** against a white row, where WCAG 2.1 AA wants **4.5:1** for body text. Both are used throughout: job-status rows, connection-test results, divergence rows, change-control field marks. `has-text-*-dark` is high-contrast but goes muddy for some hues (`has-text-warning-dark` is `rgb(41,29,0)` — effectively black, so a "warning" reads as ordinary text). **Not introduced by any one feature** — it is the palette, so fix it in one pass rather than per-surface, otherwise the fixed surfaces become the inconsistent ones. **Scope:** decide the light-background token set (likely a custom `--bulma-*-on-scheme` override in `web/sass/main.scss`), verify each semantic colour at ≥4.5:1, and sweep the `has-text-*` usages. Where the colour is decoration rather than the only signal, prefer a `tag` — the change-control field mark went that way and reads far better. **Check dark mode too**: whatever is chosen has to hold on both grounds. |
| Catch an accidental duplicate proposal at creation | **Trigger: 2026-08-31.** A developer proposed the same edit twice and the queue showed two rows identical in every column. The display half is fixed (id column, changeset-derived titles, relative age), but the underlying event — *the same author proposing an identical changeset for an entity that already has one open* — is a double-submit, not a disagreement, and orbital says nothing. **Deliberately NOT a block:** two people proposing different changes to one entity is legitimate and must stay possible; even the same author may want a second, different proposal. The narrow case worth catching is **same author + same open request + byte-identical changeset**. **Preferred shape:** fold it into the amend flow (row above) — on `POST /change-requests`, if that exact match exists, respond with the existing request and let the client offer *"you already proposed this — update it instead?"*. That turns a duplicate into the amend the author probably wanted. **Do not** compare titles; they are derived and cosmetic. Compare the normalised changeset. **Acceptance:** proposing an identical still-open changeset twice surfaces the existing request rather than silently creating a second; two DIFFERENT proposals on one entity are still both allowed. |
| Amend a change request's CHANGESET from the UI | **The rename half shipped 2026-09-01** — the review page renders `edit` from `availableActions` as a **Rename** button that PATCHes `title` alone, which leaves the changeset, the base anchor and every approval untouched. What is still missing is editing the **changes**. `PATCH /api/v1/change-requests/{id}` already accepts a replacement `changes` array, so the server half is done and is the subtle part: supplying `changes` re-captures the base, so prior approvals stop matching the hash and stop counting — the same way GitHub dismisses stale reviews on a new push. So an author who wants to change *what* they proposed must still close and re-propose, losing the request's history and burning a number (`max()+1` never reuses). **The design decision is WHERE the edit happens.** (a) A changeset editor on the review page — direct, but a second editing surface with different affordances from the entity editor people already know. Reuses the surface people use, and it is the real fix for duplicate proposals, which the field marks currently only *warn* about. **Acceptance:** an author can change a proposal's changeset without closing it; approvals cast against the old changeset stop counting and say so; a second proposal on an entity that already has one is offered as an amend first. |
