# UI Reference

Read this before: Go template changes, HTMX interactions, JavaScript, CSS/SCSS, any frontend work.

## Settled Decisions

- **Closing a tab lands on the one to its LEFT; closing a background tab moves nothing.** *(Fixed 2026-10-05.)* The close button clicked Summary unconditionally, so shutting the last of five tabs threw the reader back to the list every time, and tidying away a tab they were *not* looking at yanked them out of the one they were. Left-neighbour **terminates naturally** — the leftmost detail tab's neighbour IS the Summary tab — so the "last tab" case needs no branch. Focus moves only when the closed tab `is-active`, which is what every browser, IDE and multiplexer does. ⚠️ `replaceCurrentTab` must be given the SAME neighbour, not `tab-summary`: the persisted current tab is what the next arrival restores, and pointing it at a tab that was just removed falls back to Summary silently.
- **The active tab is stored PER SLUG, and coming back restores it.** *(Fixed 2026-10-05.)* `getTabStorageKey()` branched on `#server-list-table` — an element no orbital template has had since the migration — so **every** generic list page wrote the data-centre page's `dcTabCurrent`, while `initGenericTabRestoration` read a literal `tabCurrent` that nothing writes. The restore silently did nothing and every visit landed on Summary; the hand-written pages had always restored. Two halves, both needed: the key is `genericTabCurrent:<slug>` (the tab list has been slug-qualified since it was written — this is the same fact finally spelled the same way), and the reader goes through `getCurrentTab()` rather than naming a key. ⚠️ **Under lazy restoration this is the ONE panel that fetches on arrival** — a test asserting ZERO fetches would pass just as well for a restore that does nothing, which is exactly how this hid. Assert *one*. ⚠️ `clearTabStateOnFresh` sweeps these by PREFIX rather than naming them: a per-page key enumerated by hand is the omission that function was already caught by once.
- **Restoring open tabs is LAZY: rebuild the strip, fetch on first selection.** *(Added 2026-10-05.)* `initGenericTabRestoration` used to call `loadGenericTab` for each saved tab, and that function ended in `tabLink.click()` — so **arriving** at a list page fired one detail request per saved tab, all at once, for panels nobody had opened. Returning from another page is a fresh load, so this ran constantly. Worse than the cost: the requests went out concurrently and one was **dropped** (measured 2 of 3), and `dataset.loaded` was set OPTIMISTICALLY right after issuing — so that tab was flagged loaded, stayed blank forever, and raised no error. `loadGenericTab(label, slug, orbId, activate = false)` now builds the tab without selecting it; `loaded` is set only after the swap resolves, with a separate `loading` guard for a double click. The rule the reader sees is unchanged — **one fetch per tab per page load** — it is just paid on the click instead of on arrival, and most are never paid at all.
- **Five tabs, LRU eviction, a toast — not a refusal.** *(Added 2026-10-05.)* `MAX_GENERIC_TABS = 5` in `shared.js`. ⚠️ **Deliberately not configurable**: per CLAUDE.md's bar a setting earns its place when the default is actively harmful to an adopter, and a tab cap is not that. Five is a judgement about the STRIP, not about cost — lazy restoration already removed the cost. Bulma's `.tabs` is `overflow-x: auto; white-space: nowrap` with no overflow menu and no tab search, so past a handful it stops being navigable; ~8 fit at 1440px and ~4 at 1024px. **Evict, do not refuse**: the click that hits the cap is a reasonable thing to do, and an error would refuse it while leaving the reader to work out which tab to close — browsers, IDEs and terminals all shrink or scroll rather than say no. Safe *because a tab holds no unsaved state*. **Least recently USED, not least recently opened** — `touchedAt` is stamped on every activation, so a tab you keep returning to survives; open-order would discard exactly the one you wanted.
- **The edit modal belongs INSIDE `generic-detail-content`, not in the page block.** *(Fixed 2026-10-05.)* That block is served both as a full page and as the tab fragment, so a modal rendered outside it shipped only with the page: the Edit button inside a tab resolved no `edit-modal-generic-<id>`, did nothing, and raised **no console error**. The old hand-written `server-tab.gohtml` rendered its own modal inside itself for exactly this reason, and the migration dropped that. The opener is a delegated click handler that resolves the modal by id at click time, so nothing else needed wiring. ⚠️ **A swap invalidates any cached editor** — both the Reload button and the post-save `reloadFn` must `genericEditors.delete(id)` before swapping, or the next Edit drives a JSON editor bound to a detached node. ⚠️ `reloadFn` is tab-aware for the same reason Reload is: a blanket `window.location.reload()` from inside a tab throws the reader back to the list, and under lazy restoration the tab comes back unloaded — so the edit they just made is not even on screen.
- **`displayTabContent` touches only panels that HAVE an id — `.tab-content` is ALSO the layout wrapper.** *(Fixed 2026-10-05.)* It hid every `.tab-content` whose id did not match the target. But `.tab-content` is the house box/`min-width` wrapper in `main.scss`, so `generic-detail-content` — the body served both as a full page and as the tab fragment — opens with its own `class="tab-content"` and **no id**. Hiding that was PERMANENT: the function can only un-hide by matching an id, so nothing could ever restore it. The panel stayed `display:block` around a child that was `display:none`, and every detail tab went blank the instant a second one opened. ⚠️ **The tab STRIP keeps working throughout**, which is why the existing tab tests all passed — a test that asserts the strip proves nothing about the panel. Assert the panel is `:visible`: an element whose only child is `display:none` has no box, so that is the probe that distinguishes them. Pinned by *switching back and forth between tabs keeps their contents*.
- **The `/views` page AND `GET /api/v1/views` are both DELETED.** *(2026-10-05.)* The page existed because views were derived from schema docstrings and it was the only window onto what orbital had derived; `config/views.yaml` replaced that premise. The endpoint went with it, for a different reason: **nothing consumed it** but that page, and its shape was designed for that page — keeping it would freeze a published contract around a requirement that no longer exists. ⚠️ **The endpoint was NOT a copy of the file** and "serve the yaml instead" would be strictly less: half of what it returned (`fields`, `display`, `tableHidden`, `meta`, `contains`, `isInterface`, resolved `label`) is derived from the deployed schema, and the declarations are already readable in git. ⚠️ **The counter-argument, recorded because it may come back:** this file's own API-first rule says a client must be able to render what orbital renders without re-deriving it, and AEP building its own server table now has to re-derive labels, column order and editability. That was judged speculative against zero consumers — **if AEP asks, add it back shaped for AEP**, not shaped for a dead page. ⚠️ **The page had already rotted within two days** of the model changing: its description still said pages were *derived* after they became declared, and its `Source` column read "derived" on every row forever, because the override layer it anticipated shipped as files instead. That is the cost of a diagnostic in the primary nav that nobody owns. **What replaced both:** the boot log's `resolved views …` line now names the resolved page slugs, not just counts — the merged result of file × overlay × deployed schema exists nowhere else, and that is where someone debugging already looks.
- **A ConfigItem is shown as a TAB and nowhere else. `/{slug}/{orbId}` is the url the tab FETCHES, and it 404s for a human.** *(Settled 2026-10-05.)* Rows link to **`/{slug}?open={orbId}`**; the detail path appears in no href anywhere. ⚠️ **An href is a human-facing surface whether or not you mean it to be** — ⌘-click, middle-click, *copy link address*, *open in new tab*, the status bar, a screen reader announcing the target — so "this url is internal" and "every row links to it" cannot both be true. A redirect was tried first and is a half-measure: it makes arriving graceful instead of removing the arrival. **The fix is that nothing links there.** `generic-detail.gohtml` therefore has NO `{{define "page"}}` block, and every render in `Detail` is a fragment, error paths included — a full-page render swapped into a tab nests a menu inside a panel. ⚠️ This is what the hand-written pages did: their handler was literally named `Tab` and a non-htmx request was redirected away. A viewable per-entity page existed only between 2026-09-29 and 2026-10-05, as a side effect of making every type routable, and it left two layouts for one thing. ⚠️ **Do NOT justify this by "the API is GraphQL so there is no REST resource"** — UI urls address VIEWS, not resources (GitHub's UI is path-shaped over a GraphQL API), `?open=` is equally a per-entity url, and `DELETE /api/v1/config-items/:type/:id` already exists. The reasons that hold are: the path is the tab's fetch, and one view model beats two. ⚠️ **`?open=` is stripped from the address bar once honoured**, so there is deliberately no copyable per-entity link anywhere in orbital — confirmed as wanted, not an oversight.
- **Overriding a DataTables style: read ITS css first, and scope to the WRAPPER.** *(Added 2026-10-05, after three wrong attempts.)* DT2 types each column from its **data** and gives numeric/date ones `dt-type-numeric`, which does **two** things — `text-align: right` on the cells *and* `flex-direction: row-reverse` on `div.dt-column-header`, which moves the sort arrow to the left. Fixing one leaves the other, and the symptom changes rather than going away. ⚠️ **Scope to `#generic-table_wrapper`, never `#generic-table`**: under `scrollX` DataTables clones the header into an id-less table inside `div.dt-scroll-head` and leaves the original `thead` hidden for sizing, so a rule scoped to the table id styles the **invisible** copy — cells change, header does not. ⚠️ **`columnDefs: [{ className: 'dt-left' }]` looks like the library-idiomatic answer and does not work** — the class never reaches the cloned header. Tried and reverted. ⚠️ It is **data-driven**, so it comes and goes: the clusters list's `Nodes` column looks normal only because some clusters render "—". Do not chase it as a template bug.
- **DOUBLE click opens a row as a tab, because SINGLE click is already DataTables row selection.** *(Settled 2026-10-05.)* `initGenericTable` sets `select: { style: 'os' }` and the Copy/Excel/CSV buttons export the selection when there is one — so single click has a meaning, and it is load-bearing. The hand-written tables carried the same `select` line and opened on double click: that was **forced, not a preference**, and the reason was invisible until someone looked. A single-click opener was added 2026-10-04 (to fix rows that navigated away, which was a real bug) without checking what the gesture already meant; it fired selection AND opening from one click, and would have made selecting a row impossible once the link came out. Removed the next day. ⚠️ **Before binding a gesture on a DataTable, check `select`** — the conflict is silent: both handlers run, both "work", and the damage is that one of them can no longer be performed alone.
- **A list row's NAME is PLAIN TEXT; the row carries `data-orb-id`.** *(Settled 2026-10-05.)* A link there would claim a navigation that does not happen — the tab opens on the page you are already on — and an href is a human-facing surface regardless of intent (⌘-click, middle-click, *copy link address*, the status bar), which is how the detail path leaked back out after being made 404. With the name plain, **blue means exactly one thing in that table: you leave this page.** Reference cells still link, because those really do (`?open=` on another type's list); a reference to a type with no page renders as text. ⚠️ The row is the handle now — `labelOfRow` reads the first cell and the dblclick handler reads `data-orb-id`, because there is no href left to parse. Pinned by *a single click SELECTS the row; it does not open anything* and *the name cell is PLAIN TEXT — no row carries a link to itself*.
- **The detail page's action row sits at the TOP of the shared body, and Edit is `is-rounded is-link`.** *(Restored 2026-10-05.)* The migration moved Edit/Delete into the Fields box header and recoloured Edit `is-success`. Both were wrong: `generic-detail-content` is served **both** as a full page and as the tab fragment, so burying the buttons inside a box moved them in both surfaces at once, and green contradicts this file's own *"primary-action buttons use `is-link`"* rule — no hand-written page ever used `is-success` for Edit. Order is action row → pending-changes banner → Fields, which is what `server-tab.gohtml` had. The banner stays directly under the buttons because it changes what Edit will do.
- **ONE Reload button serves both the full page and the tab, and resolves which at CLICK time.** *(Added 2026-10-05.)* The detail route serves a whole page and — under `HX-Request` — just its body, so the button has to mean two things. The handler looks for the `.tab-content[id^="tab-content-generic-"]` it is sitting in: found ⇒ re-fetch that panel's `data-detailUrl`; absent ⇒ `window.location.reload()`. **Deliberately not a server-rendered flag** — the template would have to know whether this render was a page or a fragment, and the whole value of the shared block is that it does not. ⚠️ The failure mode is silent and destructive: a full reload fired from inside a tab looks like it worked while closing every other tab the reader had open, so the regression test opens **two**.
- **The views config has TWO sections because there are two different questions: `pages:` and `types:`.** *(Added 2026-10-04.)* `pages:` is the list of pages, and its top level IS the menu — four entries, four URLs, four nav items, no third fact to disagree with the other two. `types:` says how a type renders **wherever it renders**, which for 16 of the 20 types is only ever as rows on somebody else's page. A type appears in `types:` because it has fields and labels; it appears in `pages:` because someone decided it deserves a URL. **The nested alternative — one block per type carrying both — was argued and rejected**: `Server` renders inside DataCenter, NetworkDevice, Rack and KubernetesNode tables, so its column order, labels and reference columns would have to be repeated in all of them (13 duplicated blocks across the shipped config), and the duplicates drift silently because nothing compares them. ⚠️ **`types:` INHERITS along interfaces** — `ConfigItem: fields: orbId: {label: Orb ID}` is declared once and applies to all 20, because DGraph forbids an implementor from redeclaring an interface field, so there is nowhere else it could go.
- **A row links IF AND ONLY IF its type has a page. No page ⇒ dead rows, and that is the correct outcome.** *(Added 2026-10-04.)* `/idrac-settings/<id>` and `/storage-devices/<id>` existed only because the derivation made every type routable; they were never pages before and are not pages now. A StorageDevice renders as a row on the Server page's Storage Devices tab, its scanned fields and all, and clicking it does nothing. The templates branch on an empty `Slug` (`{{if $slug}}<a …>{{else}}{{index . "name"}}{{end}}`) in **three** places — the summary rows, the tab rows and the list-table reference columns — and missing one leaves `href="//colo:…"`, a link to a route that 404s. ⚠️ **Promoting a type to a page is a one-line change** (`pages:` entry), and it turns every dead row of that type into a link everywhere at once.
- **A ConfigItem page is a declared SUB-SUBGRAPH, and `config/views.yaml` declares it.** *(Added 2026-10-04.)* Three nested scopes: the GRAPH, the SUBGRAPH (everything reachable from a Namespace node — the export boundary, structural, never policy-driven), and the SUB-SUBGRAPH (what one page shows and edits). **Only the third is a view.** Eleven of the schema's thirteen docstring annotations were that third thing and have moved out: `slug:` `label:` `order:` `tableHidden` `include:` `editable:` `filterBy:` `column:` `viewIgnored` `menuWeight:` `editorIgnored`. A twelfth, `derivesIdFrom:`, was deleted outright — it was wrong on the one type that still carried it, and nothing read it. **The schema keeps TWO**: `jsonString` (what a String CONTAINS) and `orbIdSuffix:` (identity). Thirteen → two. Stated plainly: **DGraph rejects unknown directives, so view configuration was being smuggled through description strings** — a channel designed for documentation. `menuWeight:` was the proof; a menu position is not a property of a graph type by any reading. The split gives each its own cadence — a schema change is a version bump, an apply and reindex care; a views change is a file edit picked up with no schema operation.
- **OWNERSHIP IS DERIVED from a NON-NULL back-edge, with one declared exception.** *(Added 2026-10-04, replacing "editable means deleted".)* `Child.parent: Parent!` is the schema stating that the child has no existence without the parent — 13 of orbital's 14 ownership relations say it already, and re-saying it in the views file would be a second place to get it wrong. The P1 model routed ownership through `editable:`, which meant a **display** decision moved a **delete** boundary: dropping a tab from a page silently stopped deleting that child. Four back-edges were made non-null in schema v14 to close the gap the derivation exposed. ⚠️ **The one exception is declared, because nullability cannot express it**: `NetworkInterface` belongs to a `NetworkAdapter` **or** a `Server` **or** a `NetworkDevice` — an XOR, so every one of those edges must be nullable and none of them can carry the statement. It is the whole content of the `ownerReferences:` section. ⚠️ **`StorageDevice.storageVolumes` is a TEMPORARY second entry** — `@hasInverse` does not backfill, so the v13 `StorageController.storageVolumes` edge is empty for all pre-existing data; filed as Med debt pending a backfill.
- **The DELETE CASCADE follows CONTAINMENT, and nothing else.** *(Added 2026-10-04; the membership framing superseded above.)* No `cascade:` key, no second rule: there was never a second question. It replaced `dcDeleteGQL`/`srvDeleteGQL`/`clusterDeleteGQL` and a three-way `switch` on literal type names — ~770 lines that consulted no model and had drifted into four silent defects, every one of them a child left holding a NON-NULL edge to a deleted node: a server delete orphaned its NICs, its SCP and its KubernetesNode; a data-centre delete orphaned its network devices; and the same IPAddress was preserved by a server delete and destroyed by a data-centre delete depending only on which page you clicked Delete on. ⚠️ **An IPAddress is editable nowhere**, deliberately — four types claim one, so no single page owns it, and under this model owning it would destroy it. That is the same argument that renders it as a link rather than inline.
  ⚠️ **What is DELETED comes from the view; what is CLEARED comes from the SCHEMA.** The cascade walks every relationship with a declared `@hasInverse`, not just the owned ones: a node pointing at something being deleted is stranded whether or not a page chose to show that edge (`ServerConfigurationProfile` is listed by no view and still needs its back-edge cleared). Only TRUE survivors are cleared — when both ends die the stale edge is unreachable, and clearing it anyway puts one node in both halves of the upsert, which the version guard reads as a concurrent edit and refuses the whole delete.
  ⚠️ **The constraint that makes the one-sentence model safe lives in the SCHEMA:** a child whose back-edge is non-null is owned, by derivation — there is no view declaration that can fail to say so. Without it, omitting a child is a silent data-corruption path; with it, the only way to strand a non-null edge is to violate a rule the build already catches. **Relaxing the edge to nullable is how a child opts OUT** — `ServerConfigurationProfile.server` became nullable in v13 for exactly that reason, which is also what lets the Server view leave it off the page.
- **TWO RULES, not one per field: scalars are SUBTRACTIVE, relationships are LISTED.** *(Added 2026-10-04, replacing "ONE AXIS: membership, with attributes".)* A page shows **every** scalar its type has unless `summary.ignoreFields` removes it — a new scalar appears without anyone editing the views file, which is the behaviour you want for the 40-ish fields nobody has an opinion about. A relationship shows only if `summary.refs` or `tabs` names it — a new edge appears nowhere until somebody decides where, which is the behaviour you want for the thing that changes the page's shape. The asymmetry is deliberate and is the single most load-bearing choice in the format: inverted, the file would carry 200 field names and every schema addition would silently vanish. `viewIgnored` becomes an edge that is simply not listed; `include: a.b` becomes a tab whose path has two segments. ⚠️ **If a change makes the vocabulary GROW, the framing is wrong** — that is the test this model is held to, and it went 13 annotations → 2.
- **`editable:` means ONLY "this page's editor may write this". It no longer means ownership.** *(Added 2026-10-04, narrowing the P1 meaning.)* Ownership is DERIVED (next entry), so `editable:` stopped carrying three jobs and carries one. ⚠️ **The editor is gated at the TOP LEVEL only; below it, CONTAINMENT governs.** A page declares which of its own children its editor may reach; a wrapper two hops down (`ClusterBackup`) has no page and can declare nothing, so reading `editable:` at every level emptied the cluster editor — the data tree carried `backup.etcd`, the target list did not, and a changed etcd schedule was accepted and written nowhere, with no error and no audit row. `View.EditorMembers()` is the top level, `View.DependentSingles()` is every level below it, and `BuildEditTargets` and `attachGenericEditor` must walk the SAME rule or the tree shows a field no target can write. Pinned by `TestEditTargets_WrapperDescentFollowsContainmentNotThePage`. ⚠️ **`editable:` on a LIST tab is refused and SAID** — a target is addressed by path and a path cannot name one row — the tab renders read-only and the load warns. Silently clearing the flag leaves a page that reads as configured for an edit that never arrives.
- **`SummaryRefs` and `RefColumns` are TWO SURFACES; both are DECLARED, in different places.** *(Added 2026-10-04; the derivation removed 2026-10-05.)* `SummaryRefs` is a PAGE fact — `pages.<T>.summary.refs`, the relationship rows beside the fields, because only the page can say which of a Server's six edges belong next to its hostname. `RefColumns` is a TYPE fact — `types.<T>.refColumns`, the reference *cells* a row of this type carries **wherever it renders**, because a Server row keeps its columns inside a data centre's tab and a network device's, and declaring that per page would be the same list three times. ⚠️ **RefColumns was briefly DERIVED (every single-cardinality edge to a ConfigItem) and that was wrong** — it put `Idrac Settings` and `Server Configuration Profile` on the servers list, which no hand-written page ever showed, and meant an edge added to the schema silently widened every table of that type. "It is a property of the TYPE, not the page" is true, and is why it lives in `types:`; it is **not** a reason to derive it, and the file's own rule already said relationships are listed. ⚠️ They were also briefly ONE field; splitting the page half out emptied the reference columns of every pageless type's table.
- **`tableHidden` is TYPE-WIDE, so two tables of the same type cannot show different scalars.** *(Stated 2026-10-05; renamed from `detailOnly` 2026-10-06.)* ⚠️ **NOT `summaryHidden`** — a `tableHidden` field still renders in the detail SUMMARY panel, so that name would assert the inverse of the behaviour, and `pages.<T>.summary` already names that panel. The key is about TABLE columns, in both the places a table appears: the list page and a relationship tab. `ColumnFields() = Display − TableHidden`, and it feeds the list page **and** every relationship tab. The hand-written pages could differ — `/servers` showed no Rack Position column while the data centre page's servers table did — and that is **not reproducible**, by design: a per-page scalar list would duplicate `types:` on every page that renders the type, which is the duplication the two-section split exists to prevent. Where the two disagree, **keep the column**: an extra one is a smaller harm than a missing one. ⚠️ **An interface list page unions its implementations' columns, and that union must use `ColumnFields()`, not `Display`** — taking Display let a field declared `tableHidden` on an implementation reappear on the one page that unions several types.
- **Inline-vs-link is DERIVED from ownership, never declared.** *(Added 2026-10-04.)* `ViewSet.ExclusivelyOwned` counts how many types CONTAIN a type: one page renders it inline, several means it is a record in its own right and gets a link. Making it a config key would be a second axis for a question the first already answers. An interface and its implementations count ONCE — `ClusterBackup.cluster` is typed by the `KubernetesCluster` interface and every implementation answers to it, so counting them separately would make every backup sub-kind a link on the only page that can edit it.
- **A type with NO view entry is a statement, not a gap.** *(Added 2026-10-04; amended the same day for pages.)* It still RESOLVES — a type always does, which is what keeps its display config available the day a page does list it — and it still renders its own scalars wherever it appears as rows. With no `pages:` entry it has no URL and no menu entry. That is how a deployment says "not on the menu, nothing hangs off it". It reverses spike 38's "define a type, get a working page with no config" for the relationship half, deliberately: being able to leave something OUT is the capability `viewIgnored` was invented for, and omission says it directly.
- **A page and a menu entry are ONE FACT. `View.IsRoot` is deleted, and so is `isRootType` before it.** *(Added 2026-10-04.)* The top level of `pages:` is the menu, so "has a slug" and "is in the nav" cannot disagree — and a second field alongside `Slug` could only restate it or lie. `menuWeight:` orders the menu; it does not decide membership. Call sites ask `v.Slug != ""`. The ORIGINAL derivation guessed from ownership and its own comment admitted it: *"ownership direction is not derivable from the schema, so 'no declared owner' is the only honest answer available, and erring toward VISIBLE beats erring toward hidden."* It produced 23 routable types and a nav that had to be filtered back down to four. ⚠️ The Views page's "In nav" column went with it — its own comment said it always agreed with the Slug column, which is the tell. (That page is gone entirely as of 2026-10-05.)
- **Two layers, both FILES, no database. The overlay is PARTIAL.** *(Added 2026-10-04.)* `config/views.yaml` ships in the image; `ORBITAL_VIEWS_OVERLAY_PATH` points at a per-deployment ConfigMap that declares **only the views it changes**, replacing them **per view**. Per view, not per key: a declared view is a coherent statement about one page, and merging key-by-key would make "remove this member" — the likeliest customisation — inexpressible without a tombstone syntax. **A whole-file copy freezes that deployment forever, with no signal** — spike 38's "store overrides ONLY, never seed", applied to files exactly as it applied to rows. ⚠️ **Mount the DIRECTORY, not a `subPath`**: the kubelet updates a volume-mounted ConfigMap in place, which is what makes a view change take effect without a rollout restart; subPath mounts are not updated.
- **Views are NOT editable in the product, and NOT audited by orbital.** *(Added 2026-10-04, reversing spike 38's P1.)* That P1 was Postgres rows edited at runtime with RBAC, an audit event per change and a reset path — all governance orbital would have had to build for its own configuration. A ConfigMap is already governed: cluster RBAC decides who may edit it, GitOps decides review, `git revert` is the reset. Rebuilding that inside orbital contradicts CLAUDE.md's rule about duplicating a capability the adopter already has, and it is where the ecosystem went (Grafana's dashboards-as-code replaced the click-to-edit-and-persist model spike 38 was imitating). **Accept explicitly: view changes are audited by git and Kubernetes, not by orbital's audit log.**
- **The views config is VALIDATED against LIVE introspection at load. Never fatal, never silent.** *(Added 2026-10-04.)* Annotations had one property worth keeping — a declaration and the schema it described were the same artifact, deployed together, unable to disagree. A separate file loses that: orbital derives from the DEPLOYED schema while views come from a file, and they can be different versions with nothing saying so. A tab or ref naming a missing field, a path deeper than two segments, a `canonicalParent` edge that does not exist, a page whose type is gone, `editable:` on a list — each is **dropped or refused, and logged**. A stale view must never stop a page rendering; a declaration that reads as correct and does nothing is worse than one nobody wrote. ⚠️ `schemaVersion` is the COARSE signal only — `schema/VERSION` is bumped by hand and deliberately not for every change, so two schemas can share a label. It says "look"; per-member validation is what catches a stale path. ⚠️ **A tab path through a LIST is legal and is the headline case** (`storageControllers.storageDevices`); do not harmonise it with the `columns:` rule, which forbids list hops because a column produces one CELL and a tab produces ROWS.
- **A save whose VIEW moved since the editor opened is refused (409), scoped to the editor.** *(Added 2026-10-04.)* `configitem-editor.js` decides a field was CLEARED by diffing the open-time snapshot against the edited tree, so a tab dropped from a page while a modal sat open reads as a deletion and the save emits `remove` for fields nobody touched. The modal carries `data-views-hash`; the editor sends it as `X-Orbital-Views` on every write; the GraphQL proxy compares it after a rate-limited re-check and refuses on mismatch. The entity-version pre-flight is the same move one level down — this applies it to the SHAPE of the tree rather than its contents. **A request without the header proceeds**: an API client, orbctl or AEP sending an explicit `remove` is doing it deliberately, and gating the public API on a UI concern would be the wrong trade. ⚠️ The comparison must use the RE-CHECKED hash, not the cached one — the cached value is exactly what a stale page agrees with. Pinned by `TestEditorSave_RefusedWhenViewVersionMovedAndDropsNothing`.

- **A field's label is title-cased from its name; `fields.cni.label: CNI` in the view overrides it.** *(Added 2026-09-26; moved to the views config 2026-10-04.)* Title-casing handles almost everything (`serviceTag` → "Service Tag") and cannot know an acronym — `cni` → "Cni", `oobIP` → "Oob IP". Adding a rendering CASE was the thing to avoid; see [[feedback-fewer-cases-over-parity]]. - **Proposed-change marks and the change-in-flight banner are page-agnostic, and driven entirely by DOM attributes.** *(Added 2026-09-26.)* A table declares `data-field-orbid` and `data-field-values` (the entity's RAW editable values), each row `data-field` plus a `.js-field-mark` slot, and `loadFieldMarks` in `orbital.js` does the rest; `[data-pending-changes-for]` is the banner's placeholder. **Raw values, not rendered ones** — a mark is suppressed when the proposal already equals the current value, and comparing a proposed `5` against the string "5" the table shows would be a guess. **Only EDITABLE rows get a slot**: a mark on a field nobody can propose could never fire. - **Column and field order is a PARTIAL order pinned in the view: `order: [a, b, c]`, rest alphabetical.** *(Added 2026-09-26; moved to the views config 2026-10-04.)* Named fields lead in the order given; everything else falls in behind them, alphabetically. **Never a complete ordered list** — a complete list is a frozen view: a field added in a later release has no place in it and silently never appears. NetBox carries exactly that cost with its saved `columns` lists (open issues on layouts that cannot be modified without resetting, and on stale preferences naming fields that no longer exist). A prefix leaves the tail open, so new fields still arrive.
  The pin lives in the **schema**, not a database, because a default belongs in version control — it ships with the build, it diffs, it reverts. An interface's pin is **inherited** by its implementations (a type docstring does not propagate on its own), which is what keeps `/clusters` — an interface view — ordering its columns the same way each concrete detail page does. A list page re-applies the pin to the **union** after merging implementation columns, or an implementation-only pinned field (`clusterType`) lands appended at the end in the one position the schema said it should not be.
  A pin naming a field the type lacks is **skipped, not an error**: an interface's list is inherited by implementations that legitimately lack their siblings' fields. ⚠️ **`UI.md`'s older "identity fields first" rule named those fields in a per-type list in this document** — that is the hand-maintained form this replaces; do not reintroduce it.
- **A relationship table drops the column pointing back at the entity whose page it is.** *(Added 2026-09-26.)* A cluster's Nodes table carried a `cluster` column reading the same name on every row, and its Workload Clusters table a `managementCluster` column doing the same — you arrived by clicking that entity, so the column is guaranteed to name it. Pure width; on the workload table it was part of what pushed 13 columns past the container.
  **Two conditions, both required:** the column's target type is the page's type (or an interface it implements) AND *every row actually points back*. The data check is what makes it safe — a type can hold two references to the same kind and only one is the edge you traversed — and it avoids needing `@hasInverse`, which introspection cannot see. A row MISSING the reference keeps the column: an absent link is information, and hiding the column would hide it. **Columns that are merely empty are NOT dropped** — that would make the column set shift with the data, so "nothing here has notes" becomes invisible rather than visible-and-blank.
- **A view may be backed by a GraphQL INTERFACE, and then it lists every implementation.** *(Added 2026-09-25.)* `/clusters` is the `KubernetesCluster` interface's view, not `EksaKubernetesCluster`'s. The constraint that shapes it: DGraph generates `query<Interface>` but **no `get<Interface>`** — a `get` needs an `@id` field and `orbId` is declared on `ConfigItem`, not on the sub-interface — so an interface view backs a **list page only**. Its detail route resolves the row's concrete type with `queryConfigItem(filter: {orbId: {eq: …}}) { __typename }` and renders with THAT type's view, so one URL family (`/clusters/<orbId>`) serves every implementation. List columns are the **union** of the interface's scalars and each implementation's own, selected through `... on <Impl> { … }`; a row whose type lacks a column renders `—`.   **An implementation is demoted out of the nav** when an interface view covers it: two entries showing identical rows today would diverge the day a second provider lands. Its pages stay reachable by URL. **Do NOT solve this with a slug alias instead** — aliasing `EksaKubernetesCluster` to `/clusters` passes the duplicate-slug check and is still wrong, because the page would silently omit every other provider. - **Every ConfigItem detail page carries a derived metadata box and an audit box.** *(Added 2026-09-25.)* The metadata rows are `View.Meta` — the `ConfigItem` interface fields, read from the deployed schema — so a field added to the interface appears without a template change. `displayScalars` strips those fields out of `Display` deliberately; the metadata box is the other half of that decision, and without it they were on no page at all. - **A multi-entity Save PRE-FLIGHTS before it writes anything, and dispatches SEQUENTIALLY.** *(Added 2026-09-16.)* `configitem-editor.js` used `Promise.all`, so every mutation landed regardless: a failure on the second left the first and third committed while the operator was told "Conflict — please reload". Now one aliased `query{Kind}` reads the current `version` of every entity the save will touch and refuses the whole save if any moved — naming them — before the first write. That shrinks the exposure from **modal-open → save** (minutes, while a human reads a form) to **pre-flight → write** (milliseconds). Dispatch is then sequential fail-fast, so anything after a failure never fires, and the error names which entities **did** land. **Do NOT restore `Promise.all`** — parallel dispatch makes the blast radius every other entity in the tree.
  ⚠️ **This is not atomicity and must not be described as such.** Each GraphQL mutation is atomic on its own, but a multi-entity save is SEVERAL of them and nothing binds them together ([DGRAPH.md](./DGRAPH.md)), so a genuine outage mid-sequence still partials — now reported rather than silent. The pre-flight is also **not a security control**: the server's per-mutation `version` check is, and it still runs. This only stops orbital writing half a tree.
- **The policy pre-flight asks about EVERY type in the edit tree, not just the root.** *(Added 2026-09-16.)* `/api/v1/approval-policies/resolve` takes a repeatable `type` param. Asking about the root alone made a type-scoped policy on a child invisible: the modal offered a plain Save, then the child's mutation refused `403` *after* the parent had been written — a guaranteed partial, not a race.

- **Render the server's `error` and `hint`; NEVER surface a bare status code.** *(Added 2026-09-15.)* Orbital answers every failure with one envelope — `{error, code, httpStatus, hint}` ([ERROR-RESPONSES.md](./ERROR-RESPONSES.md)) — and `hint` is the half worth showing: it is where "Open a change request: POST /api/v1/change-requests" and "Reload and try again — the delete preview is out of date" live. Use `apiErrorText(response, fallback)` for a response you have not read, or `apiErrorFromBody(body, fallback)` when you already have it; both live in `shared.js`. **Do NOT re-implement `(j.error || fallback) + (j.hint ? …)` inline** — that is how this drifted: the convention was documented server-side and enforced nowhere on the client, so seven sites copied it, four printed `HTTP <status>` instead, and new code inherited whichever neighbour it was copied from. **Never render `code`** — it is the machine identifier clients branch on, not prose.
- **An aborted request (status 0) is not an error to display.** *(Added 2026-09-15.)* A superseded fetch or a page being navigated away from produces status 0 and no response body, so there is nothing to render and nothing the reader can act on — showing it buries the errors they can act on. `apiErrorText` returns `''` for this; treat `''` as "say nothing". Burn: the change-request queue initialised a DataTable with an `ajax.url` (which loads immediately) and then called `.load()` again, aborting the first request — the user saw **"Could not load change requests — HTTP 0"** on a working page. **Resolve a table's initial filter BEFORE constructing it**, so there is one request, not two.

- **A list table is a DataTable, fed by a SERVER-CAPPED fetch and paged client-side.** *(Added 2026-09-15.)* Inventory, data centers, servers, clusters, network devices and the audit log all do this; the change-request queue was the last hand-rolled `tbody.innerHTML` table and the only long list with no paging, search or sort. The cap is a query param on the fetch (`?limit=200`, as the audit log does). **Do NOT add a `<colgroup>` to a DataTable** — `autoWidth` sizes the columns and the two fight; colgroup is for the hand-rolled tables only. `scrollX` is per-table, not a rule: it is for tables that overflow, and it clones the header, which breaks `#id thead th` selectors.
- **A capped fetch must SAY it was capped.** *(Added 2026-09-15.)* `?limit=200` showing the first 200 of 531 looks exactly like a complete list. The change-request queue renders "Showing the 200 most recent of 531 — narrow with a tab or the search box" from the response's `total`. Silent truncation is refused elsewhere in this codebase (`"Refused, not truncated"` on the orbId filter); a list view should not be the exception.
- **Sort on the raw value, render the display form.** *(Added 2026-09-15.)* A column showing an age ("3d", "10h") or a count must use `render: (v, type) => type === 'display' ? pretty(v) : v`, so DataTables orders on the timestamp rather than lexicographically on the label. Getting this wrong produces a sort that looks plausible and is wrong.

- **Do NOT convert one page's graphdiff rendering from JS to Go templates in isolation.** *(Moved here from `debt.md` 2026-09-15.)* The graphdiff surfaces build their HTML in JavaScript rather than Go templates, against the house pattern. The conversion is worth doing, but **splitting a page across both patterns is worse than leaving it**: two places to change one row, and the JS/template pair drifts silently. Convert a whole surface or none of it. The "orbital's UI is never a privileged server-rendered path" decision does NOT forbid server-rendered HTML — it forbids the UI reaching data no API client can; the two never conflicted.
- **Do NOT bolt `data-field` rows onto a list table to reuse the proposed-change renderer.** *(Moved here from `debt.md` 2026-09-15.)* Storage and Network panels cannot surface a proposed change today because the field-mark renderer assumes a field table — one row per field. A list table is a different shape, and forcing it makes the "the two must not drift" guarantee start drifting. Give lists their own mark shape, or leave them unmarked until one exists.

- **JS module cache invalidation lives in `head.gohtml`'s `<script type="importmap">` — every cross-file relative import MUST have a matching map entry.** ES-module specifiers are static; `import from './shared.js?v={{.Version}}'` is not a legal specifier and can't be templated inside a `.js` file. Without the map, `orbital.js` gets cache-busted via `?v=` on its own `<script>` tag but its transitive `import from './shared.js'` hits stale browser cache after any deploy that added exports → runtime `SyntaxError: does not provide an export named X`. Adding a new module file `foo.js` with `import from './new.js'` REQUIRES adding `"/static/new.js": "/static/new.js?v={{.Version}}"` to the map. Cache-Control middleware on `/static/*` sends `max-age=31536000, immutable` only when the request includes `?v=` — safe because the URL itself changes on version bump. **`TestImportMapCoversAllModuleImports` in `web/importmap_test.go` fails at CI if any specifier lacks a map entry**; the test's failure message tells you exactly what line to add. See `internal/server/server.go` for the middleware and head.gohtml comment block for the reasoning.
- **Inventory namespace filter is page-level, not a DataTable column filter** — lives in the page header (above the table), uses regex search on the orbId column (`^namespace:`). Do not move it into the DataTable toolbar — namespace is a scope selector, not a column filter.
- **Vendor libraries in `web/shared/static/` use named subdirectories** — `datatables/`, `font-awesome-6.6.0/`, `vanilla-jsoneditor/`. Do not flatten into a single `vendor/` bucket. Each subdir contains only browser-required files — strip docs, type defs, LESS/SASS sources, and package.json before committing a new vendor library.
- **Go template `range` does not propagate variable assignments outward** — `$x = true` inside `{{range}}` does not affect `$x` after the range ends. Compute aggregates server-side (method on the struct). Example: `ImportRecord.DispatchErrors()` instead of a `$hasError` flag inside range.
- **Field-value row ordering in detail views: identity/hierarchy field(s) first, then alphabetical.** "Identity fields" are the non-boolean scalars that describe what the row IS (Server: `hostname`, `model`, `manufacturer`; IdracSettings: `firmwareVersion`; KubernetesCluster: `name`, `kubernetesVersion`). Hierarchy fields (parent references) come before identity fields when both apply — e.g. Server's summary starts with Data Center, THEN identity fields, THEN alphabetical for the rest. Boolean state flags always sort alphabetically. Rationale: identity-first reflects how operators scan ("which thing am I looking at?" then "what's its state?"); alphabetical fallback eliminates per-field judgment calls and stays stable as fields are added. Reference: Server summary in `server-tab.gohtml`; IdracSettings in `server-tab.gohtml`. Schema declaration order is NOT the source of truth — schema order reflects when fields were added, not display intent.
- **Field-value labels in detail views are the title-cased field name — NOT the schema name in monospace.** *(Settled 2026-09-23, replacing the opposite rule.)* The previous rule required `sshEnabled` rendered in `is-family-monospace` and cited `server-tab.gohtml` twice as its reference implementation. It was never implemented anywhere: `is-family-monospace` appeared **zero** times across all four detail tabs, including the two panels it named. It also contradicted the label rule directly below it, which the code does follow. The stated goal — API discoverability — is already met, because a title-cased label round-trips unambiguously ("Asset Data V2" → `assetDataV2`), and verbatim field names already appear in the JSON editor, the audit log and the API. Do NOT reintroduce the monospace form for detail-view keys. (List-table cells are covered separately below.)
- **User-visible UI strings use vendor-neutral terms for category-level resources, not protocol/vendor names.** Buttons, labels, page titles, error messages, and status text use "Object Store" / "object storage" — NOT "S3", "Azure Blob", "MinIO". Reason: orbital runs against Azure Blob in production (via the AWS SDK's S3-compatible client), MinIO locally, and any S3 vendor on other deploys. Writing "S3" in the UI misleads operators who'd otherwise look in the wrong cloud console. **Exclusions:** env var names (`ORBITAL_S3_BUCKET`), Go struct field names (`S3Endpoint`), and internal log keys (`s3Key`) stay as-is — they're internal vocabulary that signals "S3 protocol API" rather than "AWS S3 product," and renaming has deployment cost. Apply this rule to: user-clickable button labels, page subtitles, help text, configuration-warning messages, and error messages surfaced to the UI. Same rule applies to other vendor names that have a category equivalent (e.g., "PostgreSQL" in user UI → "database" unless the user choice of engine is the point).
- **Edit pattern — one JSON editor at the parent, no per-child Configure / Edit / Delete UI.** Parent ConfigItems (Server, DataCenter, KubernetesCluster) render a SINGLE Edit button that opens a JSON editor whose tree IS the parent + every owned-child ConfigItem nested inline. The page handler exports a `targets` JSON blob (one entry per editable entity, built by `configitems.BuildEditTargets`); the generic `configitem-editor.js` module owns snapshot/diff/dispatch. **Edits to existing entities** fire canonical `update{Kind}(orbId, set)` mutations SEQUENTIALLY (fail-fast, after a version pre-flight — see the top of this file), one per affected concrete type — **a DGraph constraint, not a style choice**: nesting a child update inside the parent's `set` is silently discarded ([DGRAPH.md](./DGRAPH.md)). ⚠️ This is still **not atomic** — a genuine outage mid-sequence partials, now reported rather than silent. See `debt.md`. **First-time creation of a wrapper + its children** (e.g. adding backup config on a cluster where `backup: null`) is folded into ONE nested `update{Root}` mutation whose `set` carries the whole subtree — do NOT decompose into parallel wrapper-link + child-add mutations. Parallel dispatch races DGraph into auto-creating a partial wrapper node that fails NotEmpty on `namespace` (real burn 2026-07-08, backup-config first-time-configure). **Do NOT add a per-child modal, "Configure" flow, or per-row Edit/Delete buttons for an owned child.** Read-only sub-tabs displaying current state are fine (e.g. cluster's Backups tab). The pattern's intentional trade-off: lower field discoverability vs forms; if it becomes unacceptable, propose a hybrid (form-with-advanced-JSON toggle) and apply it codebase-wide, never deviate for one feature. Reference implementations: Server → IdracSettings; Cluster → ClusterBackup → EtcdBackup/VeleroBackup/S3Sync. See `docs/playbooks/add-configitem.md` for the recipe.
- **Adding a new ConfigItem touches TWO files, neither of them Go.** *(Rewritten 2026-10-04.)* Declare the type in `schema/schema.graphql`, give it a view in `config/views.yaml`, and stop. The audit allowlist, the editable field set, the before-fetch selection, the page, the tabs, the edit targets and the delete cascade are all derived from those two. `configitem-editor.js` consumes the targets the view produces, so a new sub-kind touches no JS. ⚠️ **The audit allowlist comes from the DEPLOYED schema, not from the binary** — that is the point: the Go list it replaced was keyed to the SHIPPED schema, so a deployment whose DGraph carried an extra ConfigItem type got ungated, unaudited writes on it, and no build-time test could see it. See the playbook; this used to be ~13 places.
  ⚠️ **This holds for a new SUB-KIND under an existing parent. It does NOT yet hold for a new PARENT family** *(corrected 2026-09-14 — the claim was unqualified and read as covering both).* A new parent today needs a 5-file copy: its own `edit-modal-<kind>.gohtml`, a handler parse-line, and a per-type opener in `orbital.js` keyed on `edit-modal-<prefix>-<id>`. Two `debt.md` Track A items are what make the unqualified claim true — consolidating the four edit-modal templates into one, and registry-driven orbId derivation. Until both land, qualify this promise when you repeat it.
- **Clearing a field emits `remove`, not `set: null`.** On save, `configitem-editor.js` diffs each target's current JSON against its open-time snapshot: non-empty fields → `set`; fields that were set and are now empty — `null` / `""` / a deleted key, all equivalent — → `remove: { field: <snapshot value> }`. Required because DGraph **ignores `null` in a `set` patch** and **rejects `""` on typed scalars** (`DateTime`); `remove` matches on the value, and the open-time snapshot holds the current one. One `update{Kind}` carries both `set` and `remove` (one audit row), and the `set` still receives the server-stamped `version`/`updatedAt`/`updatedBy` — so a clear is a normal audited edit. See `removePayload`/`scalarPayload`/`buildUpdateCall` in `configitem-editor.js`. A `remove`-only mutation is rejected `VARIABLE_FORM_REQUIRED`, so the editor always sends a variable `set` (even `{}`) alongside. **API callers do this read-then-remove explicitly** — see "Clearing a field" in `docs/api-cheatsheet.md`.
- **Do NOT use native HTML `title=""` for user-facing tooltips.** Browser-controlled — ~1s delay before display, small system font, no theming, no smart positioning. For interactive UI use the existing `.tooltip` + `data-text=""` CSS class in `web/sass/main.scss:187` (instant on hover, themeable). Long-term: migrate to Tippy.js — tracked in ROADMAP technical debt. New code MUST NOT add `title=` attributes for user-facing tooltips; existing ones get migrated when touched.
- **UI field labels stay consistent with the schema field name — do NOT invent prettier divergent labels.** A label is the title-cased field name, **preserving version/legacy suffixes** (`assetDataV2` → "Asset Data V2", not "Asset Data"). The reason is API discoverability: the same people read the UI and query the GraphQL API, and a label that hides the real field name (or drops a `V2`) sends an integrator hunting for a field that doesn't exist. When a field name is awkward because it's legacy (a rename would be a breaking schema change), the UI carries the awkwardness rather than papering over it. Fixed `assetDataV2`'s "Asset Data" label 2026-07-24. If a label genuinely needs to differ from the field, that's a signal the field should be renamed (schema change) — not that the UI should diverge.
- **Color convention — Bulma color classes are reserved for state classification.** `is-danger` (errors, failures, destructive actions), `is-warning` (needs attention, unverified, degraded), `is-success` (completed, healthy, verified), `is-info` (informational tags, neutral highlights). Do NOT apply these to ordinary value text — a cell showing a config value is not "danger" just because it differs from intent. `<code>` is rendered in default text color with a subtle background — its differentiation from prose is typographic (monospace), not chromatic. Bulma's default `--bulma-code` is overridden in `main.scss` to neutralize the hot-pink red, which would otherwise consume the danger-color channel for purely typographic styling. If you reach for `has-text-danger` on something that isn't an error, find a different signal.
- **List-table cells are plain text; only a genuine status column carries color.** In a `<table>` of records, value cells get no per-cell `is-family-monospace`, `is-size-*`, `is-italic`, `<code>`, tag pills, or value-coloring — style the row uniformly. The one exception is a real state column, rendered as plain colored text (per the color convention above — `has-text-success`/`warning`/`grey`), never a pill. The detail-view monospace-key rule (schema field names) does **NOT** extend to list-table cells. Real burn: the Spike-36 approval-policies / change-requests tables rendered namespace in monospace, the type placeholder in grey, and one cell at `is-size-7`, so every column read as a different font/colour.
- **Uniform monospace across ALL data cells satisfies the rule above — what is forbidden is PER-CELL differentiation.** The change-request Changes table renders orbId, Type, Field, Current and Proposed all `is-family-monospace`; that is one treatment, not five. It drifted back into the documented burn on 2026-09-04 (mono / sans / mono / mono / mono, plus three colours inside one cell) and was corrected by making the row uniform, not by stripping monospace. Do NOT "fix" that table to sans on the strength of skimming the no-per-cell-monospace clause.
- **An exception column renders the EXPECTED case as an empty cell.** The Changes table's `Note` column is blank for `applies`, and speaks only for `Stale` / `No change` / `Conflict`. A label repeated on every row trains the reader to skip the column — which is the column the conflict warning lives in. It is called `Note` and not `Status` because the change-request queue (`#cr-table`) already uses "Status" for the request's own status, and one page must not use one word for two unrelated things. Do NOT add an "Applies" label back.
- **A banner states the SITUATION and whose move it is; the table names WHAT.** The stale banner is one sentence ("Stale. Edit the request to re-read what changed") and the per-entity detail lives on the rows. Before moving detail out of a banner, check where else it is rendered: `staleEntities` was consumed *only* by the banner, so trimming it first would have left nothing naming the stale entity — the table gained the mark in the same change.
- **A binary state that a row can be IN uses a segmented control, never an action button.** Two adjacent buttons (`buttons has-addons`), both options visible, the active one highlighted and `disabled` — the Users-page role picker is the reference. A lone button labelled with the *action* (`Disable`) next to a column showing the *state* (`enforced`) encodes the same fact in opposite directions, so the reader has to invert one to reconcile them; and once the control shows the state, that column is redundant and should go. **Do not reach for a toggle switch**: it has the same defect the action button has — nothing on it says whether it depicts the current state or the change a click would make. Applied to approval policies 2026-08-29 (`Enabled | Disabled`). **Colour the active side by how much attention the state deserves**, the way the Users role picker ramps `is-primary` → `is-warning` → `is-danger`: green when the thing is doing its job, amber when it is half-on, `is-danger` when deliberately off. Red there does not mean "bad" any more than admin does on Users — it means *look at this*, and a switched-off control that still sits in the table looking like protection is exactly what a scan must catch. **If the state is security-relevant, confirm asymmetrically** — free to turn protection on, `confirm()` to turn it off, matching what Delete already does.
- **Primary-action buttons use `is-link`, not `is-primary`.** Add / Create / Save / Enable use `button is-link` (orbital standardized on `is-link` as its action colour — do not mix in `is-primary`). Destructive actions use solid `is-danger` (match the config-item Delete — not `is-danger is-light`); approve/reject verdict pairs use `is-success` / `is-danger`; secondary actions (Cancel, Close) are plain (no colour).
- **All HTML template rendering goes through `renderHTML` (buffer-then-write) — NEVER `tmpl.Execute` / `ExecuteTemplate` directly into `c.Response()`.** `html/template` streams output and only errors *after* partial bytes are written, so executing straight into the response commits a `200` + truncated body on any mid-render error (most commonly a template referencing a field the render struct lacks). Echo's error handler cannot touch a committed response, so the failure is **silent**: truncated HTML, no 500, nothing logged — it surfaces downstream as "a button does nothing." Real burn 2026-07-27: `cluster-tab.gohtml` rendered `.Backup.Etcd.RetentionDays` but the `backupKindTab` render struct was missing that field → the fragment truncated *before* the edit modal at the end of the template → the Edit button had no modal to open. `renderHTML(c, tmpl, name, data)` in `internal/handler/render.go` renders into a `bytes.Buffer` first: on error nothing is written and the error propagates to a real 500 (the access-log middleware escalates 5xx → ERROR, so it is visible); on success it writes the full body in one shot. Pass `name=""` to run the root template (`Execute`), or a defined-block name to run `ExecuteTemplate`. This buffering does NOT prevent struct/template field drift — it makes the drift fail *loud* (500 in dev/CI) instead of silently truncating in prod. New handlers MUST render through this helper.

- **ONE edit-modal template for every parent family.** *(Added 2026-09-23.)* `shared/components/edit-modal.gohtml` renders from `component.EditModal`, built by the page handler; the tab template calls `{{template "edit-modal.gohtml" .EditModal}}`. - **`data-modal-close` closes any modal, via one delegated handler in `shared.js`.** *(Added 2026-09-23.)* The button sits inside the modal, so `closest('.modal')` finds it — no id, no per-type attribute. ## House style — measured, not invented

**Measure the closest existing page and copy its markup. Do not derive the style from this table.** This section exists to tell you *which* page to copy and which mistakes have already been made; the templates are the authority.

| Element | Exact markup |
|---|---|
| Page heading | `<p class="is-size-4 mb-2" data-testid="page-heading">` — 24px |
| Description under it, on a LIST or TOOL page | `<p class="has-text-grey mb-4" style="font-size: 0.875rem;">` — 14px |
| Section label inside a box | `<p class="is-size-6 has-text-weight-semibold mb-3">` — 16px |
| Every table | `class="table is-striped is-hoverable is-fullwidth is-size-7"` — 12px cells, `w700` headers |
| Wide table wrapper | `<div class="table-container">` — Bulma's own `overflow-x: auto`, not an inline style |
| Record-scoped actions | `<button class="button is-rounded is-small is-link mt-1">` in a `columns m-0 > column pt-0 pl-0` toolbar at the TOP |
| List-page actions | `<button class="button is-small is-link">` — square, not rounded |

**Reference pages to copy, by shape:**

| Building | Copy |
|---|---|
| A list page | `publish-history.gohtml` — heading, description, one `.table-container` table, pagination nav |
| A page of boxed sections | `restore.gohtml` (stacked) or `schema.gohtml` (narrow box + wide box) |
| A record detail view | `server-tab.gohtml` (toolbar, then `grid` of `.box` cells) or `change-request-detail.gohtml` |
| A key/value summary | `schema.gohtml`'s "Active Version" — `column is-narrow`, boxed, `<tbody>`-only table |

- **A wide table inside a Bulma `.cell` needs `min-width: 0` on the cell.** `main.scss` sets it for both `.tab-content .column` and `.tab-content .cell`: a flex/grid child defaults to `min-width: auto` and grows to its widest descendant, which defeats the child's own `overflow-x: auto` — the container has nothing to scroll and the *page* scrolls sideways instead. The `.cell` half of that rule was added when the change-request review page put a 3-column diff in a `is-col-span-2` cell.
- **Box titles are 24px when the box IS the page, 16px when a page heading sits above it.** `server-tab.gohtml` uses `is-size-4` because a tab has no page heading, so its box titles are the largest text on the view. `restore.gohtml` and `schema.gohtml` — the two pages with both a heading and boxes — use `is-size-6`. Copying server-tab's 24px onto a page that already has a 24px heading flattens the hierarchy; that was a real defect on the change-request review page.
- **A standalone page opts into the app-wide box treatment by wrapping content in `<div class="tab-content">`.** `main.scss` scopes padding, shadow, border-top and the 1%-darker fill to `.app-main .tab-content .box`. A bare `article.box` outside that scope gets Bulma's default, whose background is the SAME colour as the page in dark mode — the card is then present in the DOM and invisible on screen. `restore.gohtml` and `schema.gohtml` both use this wrapper; it is the reason they match the server detail panels. **Do NOT write a bespoke `.box.<page>` override to fix the colour** — that was tried on the change-request review page and rejected twice for not matching the reference page it was supposed to match.
- **Boxes are NOT banned in page content.** An earlier version of this section claimed "there are no section containers", measured only from `/servers` and `/audit-log`, both list pages. `restore.gohtml`, `schema.gohtml`, `publish-history.gohtml` and orb's `status.gohtml` all box their content. Use a box for a bounded summary; leave the page's main subject (a diff, a long log) as a bare table.
- **A page description line belongs on a LIST or TOOL page, not a detail page.** On a list page it says what the list is. On a detail page it would describe the page type rather than the record, which is boilerplate. Give that slot to the record's own description instead.
- **Status renders as plain coloured text inside row-per-record tables** — `has-text-link` / `-success` / `-danger` / `-grey`, optionally with `has-text-weight-medium` (`divergence-reports.gohtml:227`, `CR_STATUS_CLASS` in `orbital.js`). A `tag` pill is correct only for a single prominent scalar in a box (`schema.gohtml`'s version). **The same value must render the same way on a feature's list page and its detail page** — a pill on one and coloured text on the other was a real defect.
- **Breadcrumbs are not used anywhere in orbital.** "Back to parent" is a rounded `is-warning` button with a left-arrow icon in the top toolbar (`server-tab.gohtml`).
- **Do NOT build page structure in JavaScript.** Containers, headings and table classes go in the `.gohtml`; JS fills element ids. The change-request review page was assembled by string concatenation in `orbital.js`, so there was no template to copy and none of the house style was inherited — it took a full rewrite plus several rounds of "this doesn't match" to correct.
- **Do NOT dim text inside a table.** Greying a field name, an arrow and a null glyph gives one row three shades and reads as inconsistency, not hierarchy — the columns already separate what is what.
- **Do NOT use `<strong>` for both section headings and inline emphasis on the same page.** Bold doing two jobs stops meaning either.
- **Do NOT add a per-cell `is-size-7`** — the table class carries it.

## Core rules

- **Inside a DataTables `initComplete`, use `this.api()` — never the outer `const` holding the table.** With `stateSave: true` DataTables restores state *during* the constructor (`_fnLoadState` → `_fnImplementState` → `_fnInitComplete`), so the callback can run before `const table = new DataTable(...)` has bound. Touching it then throws a TDZ `ReferenceError` out of the constructor and kills everything after it in the init function, including the data fetch — the table sits empty with no other symptom. It only reproduces once a saved state exists, so a fresh browser profile will not show it.
- **A cached EMPTY list is a cache miss, not a cache hit.** `sessionStorage.getItem()` returns the string `"[]"`, which is truthy — so `if (!cached) fetch()` skips the fetch forever once a page has been loaded against an empty backend. The inventory table shipped this: loaded between `make up` and `make seed` it cached `[]` and then showed "No data available in table" on every later load while every other page, which always fetches, looked fine. Branch on the parsed length, never on the raw string.
- **A page that remembers UI state across navigation uses `localStorage`, and its key MUST be added to `clearTabStateOnFresh` in `shared.js`.** That function runs on `?fresh=1`, which the login redirect sets — login is a hard boundary and one user must not inherit another's view on a shared machine. Keys in use: `datacenterTabs`, `serverTabs` (open detail tabs), `dcTabCurrent`, `srvTabCurrent` (last-active detail tab, an element id), `crTabCurrent` (the change-request queue's active filter). **A restored value must fall back when it names something no longer on the page** — the change-request queue's *Needs my review* tab is rendered only for roles that can approve, so a demoted user would otherwise land on a tab that loads nothing; the fallback is the server-rendered `li.is-active`, which the template already picks correctly per role.

- **JavaScript is split into ES modules — no bundler** — `web/shared/static/shared.js` (utilities used by both orbital and orb), `web/shared/static/orbital.js` (orbital-only features), `web/shared/static/orb.js` (orb-only features). `head.gohtml` conditionally loads `orbital.js` or `orb.js` based on `{{.UI.AppName}}`. Never inline `<script>` blocks in templates.
- **Cross-app navigation and reload handlers live in `shared.js`** — `initRowNavigation()`, `initLinkNavigation()`, and `initReloadButtons(opts?)` are exported from `shared.js` and called by both `orbital.js` and `orb.js`. Any new navigation pattern (e.g. dblclick on a new resource type) belongs in these functions so both apps get it automatically. Orbital-only edit-modal handlers (`[data-*-edit-id]` click handlers) stay in `orbital.js` — they are gated on `Actions.Edit` and must not move to `shared.js`. `initReloadButtons` accepts an optional `opts` object: `onDcReloaded(domId)` and `onSrvReloaded(target)` callbacks let `orbital.js` clean up its editor Maps on tab reload; `orb.js` passes nothing.
- **DataTables AJAX reload must guard the error path** — `dt.ajax.reload(callback)` only fires `callback` on success; errors swallow the spinner. Pattern:
  ```js
  const onError = () => reloadButton.removeClass('is-loading')
  dt.one('error.dt', onError)
  dt.ajax.reload(() => { dt.off('error.dt', onError); reloadButton.removeClass('is-loading') })
  ```
- **Click handlers default to event delegation, NOT inline `onclick=""`** — convention across `orbital.js` and `orb.js`. Endorsed by Hypermedia Systems Ch. 10 ("`addEventListener` is preferable to `onclick` for many reasons"). Survives HTMX swaps automatically; keeps functions inside the module (no `window.*` bridge needed). Pattern:
  ```html
  <button class="js-divergence-publish" data-dc-orbid="{{$dcId}}">Publish</button>
  ```
  ```js
  document.addEventListener('click', (e) => {
    const btn = e.target.closest('.js-divergence-publish')
    if (!btn) return
    divergencePublishForDC(btn)
  })
  ```
  Class form (`.js-feature-action`) is the in-house convention. Co-locate the listener block with the function it calls, in the relevant section of `orbital.js` / `orb.js`. **Three documented exceptions** where `onclick=""` / per-element `addEventListener` is allowed:
  1. **Form-submit handlers inside per-instance modal init functions** — `dc-edit-submit-${id}`, `srv-edit-submit-${id}` etc. bind via `element.addEventListener('click', ...)` inside `initEditModal()` which is called from `htmx:afterSettle`, so the rebind happens automatically on every swap. Acceptable because the binding code captures local closure state (the JSONEditor instance, the modal id) cleanly.
  2. **Inline browser-API calls** — `onclick="document.getElementById('foo').classList.remove('is-active')"`, `onclick="event.stopPropagation()"`, `onclick="navigator.clipboard.writeText('...')"`. These call browser APIs, not module functions; no bridge entry needed.
  3. **Tab activation logic captured in init closures** — e.g. `tab.addEventListener('click', () => activatePanel(...))` inside `initDetailTabs`. The closure over `panelPairs` is the cleanest way to express the relationship; rebind happens automatically because `initDetailTabs` is called from afterSettle.
- **Never add new `window.X = X` bridge entries.** The allowlist is `window.dcEditors`, `window.clusterEditors`, `window.srvEditors`, `window.networkDeviceEditors` (editor maps asserted by e2e) and `window.reloadClusterFragment` (a cross-module callable). **A module that already imports from `shared.js` must import, not bridge** — that rule retired `window.gqlErrorMessage`, `window.gqlSurfaceErrors` and `window.initConfigItemEditor` on 2026-09-23, all of which existed only because reaching through `window` was easier than adding an import. The allowlist had drifted to 8 entries against a documented 4; if it drifts again, prefer deleting a bridge to extending the list.
- **`DOMContentLoaded` inside modules works correctly** — modules are deferred by default. Use delegated `document.addEventListener('click', e => { if (!e.target.closest('#id')) return; ... })` for button handlers. Never call `getElementById` at module top level.
- **Go template + HTMX is the primary rendering pattern** — server renders HTML fragments (including `<select>` options, lists, previews); JS fetches HTML and sets `innerHTML`. Reserve JS for things Go templates cannot do: polling loops, DataTables init, JSON editors, tab lifecycle management. Never write JS to fetch data and build DOM that a Go template handler could render directly.
- **All styles go in `web/sass/main.scss`** — never edit `web/shared/static/css/main.css` directly (generated). Rebuild: `make build-css` (one-time) or `make watch-css` (watch mode).
- `make run-orbital` uses version `v0.0.0-dev` — avoids noisy git-describe strings in local dev. `make push` still uses full `$(SERVER_VERSION)`.

## HTMX patterns

- **Never use `htmx.ajax()` for programmatic tab reloads** — it carries hidden request context (triggering element, OOB swap hints, lifecycle state) designed for declarative flows. Called imperatively from async handlers, it misroutes responses. Always use plain `fetch()`:
  ```js
  fetch(url, { headers: { 'HX-Request': 'true' } })
    .then(r => r.text())
    .then(html => { el.innerHTML = html; htmx.process(el); initXxx(...) })
  ```
  Always send `HX-Request: true` so Go handlers return fragments, not full pages.

- **HTMX does not re-execute `<script type="module">` in swapped content** — use the window bridge pattern: load the library once in `head.gohtml` as a module, assign to `window.MyLib`. Applied to JSONEditor: `head.gohtml` sets `window.JSONEditor = JSONEditor`; edit modals use `window.JSONEditor` directly.

- **JSONEditor must be initialized in a visible container** — initializing while the modal is hidden produces a blank editor. Always initialize lazily on the first Edit button click (after `modal.classList.add('is-active')`), not on HTMX swap.

- **HTMX declarative attributes (`hx-get`, `hx-post`) must include `{{.BasePath}}`** — rendered server-side, they do not go through the JS `BASE` variable.

- **Two separate `afterSwap` listeners** — DC tab init belongs in the global afterSwap listener, not the `addEventListeners()` one (which is server detail page only).

## URL construction (BASE path)

- `data-*` template attributes contain only the bare path: `data-url="/servers/{{.ID}}"`
- JS always prepends `BASE` (= `window.ORBITAL_BASE` = `{{.BasePath}}`): `BASE + el.dataset.url`
- **Never include `{{.BasePath}}` in `data-*` attributes** — JS would double-prefix → 404 on AKS (`/orbital/orbital/...`)
- Exception: HTMX declarative attributes must include `{{.BasePath}}` (rendered server-side, not via JS `BASE`)

## GraphQL responses

- **GraphQL always returns HTTP 200, even for errors** — check `resp.ok` first (transport failure), then `result.errors` in the body (GraphQL-layer errors). Both checks are required. DGraph returns errors in `{ "errors": [...] }` with HTTP 200.

These patterns are used in both orbital and orb. Always use them — never invent a one-off variant.

- **Digest display** — `digest.substring(0, 19) + '…'` (keeps `sha256:` prefix + 12 hex chars). Wrap in a flex div with a copy button:
  ```js
  `<div style="display:flex;align-items:center;gap:0.25rem;">
    <span class="is-family-monospace is-size-7">${digest.substring(0, 19)}…</span>
    <button class="button is-small is-white tooltip" data-text="Copy digest"
      data-copy-value="${digest}">
      <span class="icon"><i class="fas fa-copy"></i></span>
    </button>
  </div>`
  ```

## Canonical button patterns

When adding a button that triggers an action, match the pattern below for its category. **Do not invent a new spinner / status mechanism.** Default to these unless you have a written reason not to.

### Refresh / reload button (data appears in-place)

User clicks → button shows spinner → page content swaps without navigation → spinner clears after a minimum visible duration.

- Pattern reference: `loadArtifactsTable()` (orbital.js), `loadOrbTags()` (orb.js), `refreshDivergenceReports()` (orbital.js).
- Helper: `fetchWithMinDelay(url, minMs = 500)` in `shared.js`.
- Server side: handler branches on `HX-Request: true` and returns just the fragment (a named `{{define}}` block) — see `UI.renderFragment` in `internal/handler/ui.go` and `DivergenceReports` for an example.
- Button id: `btn-refresh-*`. Spinner class: Bulma `is-loading` (added/removed by JS).
- Min display 500ms via `Promise.all([fetch, new Promise(r => setTimeout(r, 500))])`. The `.then` that does the swap must be on the `Promise.all`, **not** on the bare fetch — otherwise the swap fires when the fetch resolves and the skeleton flashes before disappearing. Mistake pattern to avoid:
  ```js
  // WRONG — skeleton flashes when fetch < 500ms because the swap fires inside the bare-fetch .then
  fetch(url).then(r => r.text()).then(html => { container.innerHTML = html })  // fires at t=fetch
    .finally(() => minDelay.then(() => btn.classList.remove('is-loading')))    // fires at t=max(fetch,500)
  ```
- **Show skeleton rows immediately** — inject a skeleton table whose `colgroup` mirrors the real table's column widths so the swap doesn't reflow. Use `<span class="is-skeleton" style="display:block">&nbsp;</span>` for cell placeholders. See `divergenceSkeletonHTML()` in orbital.js and `showDatacenterSkeleton()` in shared.js for the canonical shape.
- Always `htmx.process(container)` after swap so any HTMX attributes in the fragment get re-bound.
- Do NOT use `window.location.reload()`. Full reload doesn't match the established pattern and discards client state (open tab, scroll, expanded rows).

### Test connection / probe button (single status indicator)

User clicks → button spinner → server returns success / error HTML fragment → swapped into a result span next to the button.

- Pattern reference: backups page and divergence-reports page (`btn-test-backup-connection`, `btn-test-divergence-connection`).
- Declarative HTMX — no JS:
  ```html
  <button hx-post="{{.BasePath}}/api/v1/backup/test-connection"
          hx-target="#backup-connection-result"
          hx-swap="innerHTML"
          class="button is-light is-small">
    <span class="icon"><i class="fa-solid fa-plug"></i></span>
    <span>Test Connection</span>
  </button>
  <span id="backup-connection-result" class="is-size-7"></span>
  ```
- Server: detect `HX-Request: true`, return HTML span (`<span class="has-text-success">… Connected</span>` or `<span class="has-text-danger">… <error></span>`). Always HTML-escape the error message — see `renderTestConnectionFragment` in `internal/handler/backup.go`.
- Spinner CSS hook: `.button.htmx-request` in `main.scss` mirrors `.button.is-loading`. HTMX adds `.htmx-request` automatically while the request is in flight.
- Do NOT add `hx-disabled-elt="this"` — it sets the `disabled` attribute which interacts badly with Bulma's disabled styling and was the source of a stuck-spinner bug. CSS `pointer-events: none` in the `.htmx-request` rule already blocks clicks during the request.

### Inline status — not toast

Action-result status (Publish succeeded, etc.) shows in an existing `<div id="*-status">` notification slot above or below the action. The slot stays visible until the user navigates away or triggers another action.

- Pattern reference: `showPublishStatus()` in `orb.js`; `#publish-status` on orb's divergence page.
- Do NOT use fixed-position toasts — they vanish before slow readers see them, and we don't have a toast convention anywhere else.

### Inside an action row, a notice is TEXT — not a `.notification` panel

A tinted `.notification` next to buttons is another coloured rectangle competing with them. The edit-modal footer reached four — an amber panel above a green *Propose change*, an amber *Save directly* and a white *Cancel* — and nothing read as primary any more.

**Colour in an action row belongs to the actions.** A notice sharing that row is `is-size-7` text with an `icon-text` glyph carrying the hue: `has-text-warning` + `fa-triangle-exclamation` for something to act on, `has-text-info` + `fa-circle-info` for context. One glyph carries the urgency a filled panel did.

A `.notification` panel is still right where it OWNS its space — a page-level status slot with nothing competing (`#publish-status` above). The rule is about crowding, not about the component. Reference: `applyGateState` in `configitem-editor.js`.

## Iterating on CSS / templates

- **Static assets are aggressively cached by browsers.** When a CSS or template change doesn't appear after server restart, **hard-refresh first** (Cmd+Shift+R). The `?v={{.Version}}` cache-bust on `head.gohtml` covers _real_ deploys, not iterative dev changes within the same `Version` value. Don't chase phantom JS / HTMX bugs before ruling out cache.
- **Templates hot-reload from disk; Go handlers do not.** Editing a `.gohtml` file in dev mode picks up on the next page request. Editing a `.go` file requires restarting orbital (`make run-orbital`).

## Horizontal scroll inside flex/grid layouts (`overflow` doesn't work by itself)

When a child scroll container (`<pre>`, `overflow-x:auto` wrapper, wide `<table>`) **clips instead of scrolling** inside our `.app-main-grid` → `.columns`/`.column` layout, `overflow:auto` on the child is NOT the fix — its ancestors are refusing to shrink and expanding to the widest content. **Every flex/grid ancestor from the scroll container up to the viewport must be allowed to shrink**, and there are two distinct knobs:

- **Flex item** (e.g. a Bulma `.column`) → `min-width: 0`. Flex items default to `min-width: auto` (won't shrink below content).
- **Grid track** (e.g. `.app-main-grid`'s content column) → `minmax(0, 1fr)`, **not** bare `1fr`. A bare `1fr` is `minmax(auto, 1fr)`, whose `auto` minimum blows the track out to content width. `min-width: 0` on the grid *item* does **not** override the *track's* minimum — only `minmax(0, …)` does.

Both are needed together in a grid-of-flex layout (`.app-main` grid item has `min-width:0`, `.app-main-grid` track is `minmax(0,1fr)`, `.tab-content .column` has `min-width:0`). Diagnosis shortcut: if the box is clipping at a bounded edge with no scrollbar, walk the **entire** ancestor chain and check every flex item and grid track at once — fixing one level at a time just moves the blowout up one node. `overflow-y:auto` already computes `overflow-x` to `auto`, so the child overflow is rarely the missing piece. (Fixed for `/schema`'s SDL `<pre>` 2026-07-24.)

## DataTables + Bulma

- **Page length `<select>` needs a Bulma wrapper** — DataTables renders a bare `<select>`; Bulma needs `<div class="select is-small">` for the custom arrow. Wrap after init: `initComplete: function() { dtWrapLengthSelect(this.api()) }`.
- Use **Bulma modifier classes** (e.g. `is-small`) in `initComplete`, not CSS overrides — Bulma sizes via CSS custom properties, so `font-size` overrides don't work.
- **`stateSave: true` on all main page tables** — persists length/search/sort/position in localStorage across navigations. Applied to: inventory, datacenter, server list, audit log tables. Exclude embedded per-tab tables (e.g. `dc-servers-table`) — they reinit on every tab load.
- `.field` adds `margin-bottom` that breaks flex alignment in DataTables toolbar — avoid in toolbar layouts. `vertical-align` on `dt-length` is also ignored in flex context.

## Dark mode

Dark mode is **`prefers-color-scheme`-driven through Bulma's `--bulma-*` scheme variables** — no manual toggle. Bulma flips its scheme vars at `:root` under `@media (prefers-color-scheme: dark)` and all its own components follow automatically.

- **Never hardcode a color literal in custom CSS / templates / inline styles.** A fixed `#fafafa` / `background:white` / `#666` does NOT flip — it's right in one mode and unreadable in the other (was the clusters child-row + login-modal bug). Derive from scheme vars: `var(--bulma-background)`, `var(--bulma-text)` / `-strong` / `-weak`, `var(--bulma-border)`, the `*-on-scheme` colors, or `hsl(var(--bulma-scheme-h) var(--bulma-scheme-s) calc(var(--bulma-scheme-main-l) ± N%))` for a scheme-relative tint. Target WCAG AA (≥4.5:1) in both modes.
- **DataTables' bundled CSS assumes a light page and does NOT honor `prefers-color-scheme`.** Two burns:
  - `responsive-*.bulma.min.css` ships a generic `div.modal-content{background:white}` that **collides with Bulma's modal** (shared class, out-specifies `.modal-content`) → white frame around dark modals. Neutralized by `.modal .modal-content{background:transparent;padding:0}` in `main.scss`. Do NOT edit the vendored min.css — override in `main.scss`.
  - DataTables gates its own dark theme on `html.dark` / `:root[data-bs-theme=dark]`, which we never set. `shared.js` syncs `prefers-color-scheme:dark` → `<html class="dark">` at module load so DataTables' shipped dark rules (sort arrows, responsive detail modal, child-row borders) actually fire. Do NOT remove that sync.

## Storage conventions

- **sessionStorage** → API response data (e.g. inventory rows) — clears on tab close, always fresh on new session. Data copies go here.
- **localStorage** → UI state (tab positions, filter selections, DataTables state) — persists across sessions. User preferences go here.
- **Logout clears both** — `localStorage.clear()` and `sessionStorage.clear()` called before POST. Next login starts with no tab state.
- **Inventory sessionStorage cache + `searchCols` pre-filter** — rows fed to DataTables at init time from cache, eliminating ajax flash on revisit. Saved type filter passed as `searchCols` so filtered state is the first and only draw. Reload button clears cache, empties table visually (`clear().draw()`), then refetches. `populateTypeDropdown()` called after data is available (not in `initComplete`).

## Tab state conventions

- **Detail-tab active panel persists under `localStorage.tab-active:{tabContainer.id}`** — e.g. `tab-active:dc-detail-tabs-{DomID}`, `tab-active:srv-detail-tabs-{DomID}`, `tab-active:cluster-detail-tabs-{DomID}`. Keys are wired automatically by `initDetailTabs` (in `shared.js`); do not write them by hand. On DC tab close (`tab-close-${domId}` handler) the matching key is cleared so reopening defaults to the first panel.
- Servers page tabs persist under `localStorage.serverTabs`; DC tabs under `localStorage.tabs` — separate keys, same `TabItem` class pattern.

## Detail tabs with audit log — canonical pattern

All detail pages (DC, Server, Cluster, future) share one JS function — `initDetailTabs(tabContainer, options?)` in `shared.js` — and one set of template conventions. **Adding a new detail page is one Go template + one line of JS.**

**Template conventions** (mirrored across `datacenter-tab.gohtml`, `server-tab.gohtml`, `cluster-tab.gohtml`):

- Tab container: `<div class="tabs is-boxed" id="{prefix}-detail-tabs-{{.DomID}}">` — `{prefix}` is page-specific (`dc`, `srv`, `cluster`, …). The DOM `id` is the storage key namespace; keep it unique per entity.
- Each tab: `<li data-panel="{prefix}-panel-X-{{.DomID}}">…</li>`. First tab carries `class="is-active"`.
- Audit tab: `<li data-panel="{prefix}-panel-audit-{{.DomID}}" data-orb-id="{{.OrbID}}" data-related-orb-ids="{{.RelatedOrbIDsCSV}}">` — **the `data-orb-id` attribute is how `initDetailTabs` detects the audit tab**, so do not put `data-orb-id` on any non-audit `<li>`. `data-related-orb-ids` is optional; when present it aggregates events across the parent + nested ConfigItems.
- Panel divs: `<div id="{prefix}-panel-X-{{.DomID}}">…</div>` as siblings of the tab container. Non-default panels carry `style="display:none"`.
- Audit panel placeholder: `<div id="{prefix}-panel-audit-{{.DomID}}" style="display:none"></div>` — empty; `initDetailTabs` fills it on first activation.

**JS call site:**
```js
const tabContainer = root.querySelector('[id^="newprefix-detail-tabs-"]')
if (tabContainer) initDetailTabs(tabContainer)
```

Options (all default to safe values):
- `scoped` (default `true`) — panel lookups scope to `tabContainer.parentElement` instead of `document`. Protects against the dual-rendering case where the same entity ID appears twice on the page (e.g. a server tab open both standalone and drilled in from a DC tab). Leave true unless you can prove only one rendering exists.
- `storage` (default `'local'`) — `'local'` persists active tab across browser sessions; `'session'` resets per browser tab. Default matches user expectation ("I had Audit open; reopen the page and it's still Audit").

**Audit panel row cap** — `AUDIT_PANEL_LIMIT` in `shared.js`, sourced from `layout.AuditPanelDefaultLimit` (Go) via `window.ORBITAL_CONFIG.auditPanelLimit`. Single source of truth.

**Shared detail-tab components.** The audit `<li>` + placeholder live in
`shared/partials/audit-tab.gohtml` (`audit-tab-li` / `audit-tab-placeholder`), and the provenance panel
in `shared/components/metadata-box.gohtml` — both called with the tab's full context. The metadata box was
byte-identical in all four tabs until 2026-09-23; extracting it needed no per-type shape because every tab
struct already exposed the same field names. If you add a detail page, call these rather than copying them.

## Template conventions

- **Page titles**: `{{.PageTitle}} | Orbital` — `head.gohtml` renders this. Home page where `PageTitle = "Orbital"` renders as just `Orbital`. Every handler must set `PageTitle` in the page data struct.
- **Never redeclare fields that already exist on embedded types** (`layout.Base`) — outer field shadows embedded one and template `{{.AppVersion}}` resolves to zero value.
- **Single-tab pages** (audit log, schema, divergence reports, signed artifacts) use `<p class="is-size-4">` + `<p class="has-text-grey">` heading, not `<nav class="tabs is-boxed">`. Keep `<div class="tab-content">` wrapper if page contains `.box` elements.
- **`ShowDCBack` / `dcCtx=1` pattern** — when a server tab is opened by drilling from a DC tab, URL includes `?dcCtx=1`. Handler sets `ShowDCBack: true`, renders back button (`is-warning` class — do not change to `is-link`), sets `data-reload-url`/`data-reload-target` on edit modal so post-save reload targets DC tab content.
- **`localStorage.serverTabs` is separate from `localStorage.tabs`** — DC tabs persist under `localStorage.tabs`; Servers page tabs persist under `localStorage.serverTabs`.
- **Edge delivery page** — route `/signed-artifacts`, template `signed-artifacts.gohtml`, template key `"signed-artifacts"`. No auto-poll — manual reload button only.
- **`updatedBy` and `updatedAt` excluded from audit log variable display** (`skipVars` in `orbital.js`) — system metadata, not user-supplied input. They remain in `details.variables` in the database.
- **REST-triggered audit events have no child row** — `renderPayload` returns `null` when `details.query` absent. Expand arrow also hidden via `createdRow`.
- **Startup log must use slog, not `log.Printf`** — `cmd/orbital/main.go` calls `slog.SetDefault` before anything else so startup line emits JSON consistent with all other output.
- **Standalone unauthenticated pages still include `head.gohtml`** — a page outside the main app shell must include `{{template "head.gohtml" .}}` so they pick up `?v={{.Version}}` cache-busting automatically. Page data struct needs `BasePath`, `Version`, `UI layout.UIConfig`, `PageTitle`.
- **Full-document templates live in `pages/`, not `partials/`** — `partials/` is for HTMX fragments swapped into an already-loaded page. Anything starting with `<!DOCTYPE html>` is a page.

## Timestamp rendering

- **`data-timestamp` must use RFC3339 format** — Go's `time.Time.String()` output (`2026-06-01 19:20:52.935848 +0000 UTC`) is NOT parseable by `new Date()` in JS. Always use `.Format "2006-01-02T15:04:05Z07:00"` for the `data-timestamp` attribute. Use a short human format (`.Format "2006-01-02 15:04"`) as the visible text fallback so columns stay narrow even before JS runs.
  ```gohtml
  <span data-timestamp="{{.SomeTime.Format "2006-01-02T15:04:05Z07:00"}}">{{.SomeTime.Format "2006-01-02 15:04"}}</span>
  ```
- **`renderTimestamps(document)` runs globally at DOMContentLoaded** — a single handler in `shared.js` calls `renderTimestamps(document)` on every page load. This covers full-page renders (e.g. import history). HTMX-swapped content calls `renderTimestamps(panel)` explicitly after swap — both paths are handled.
