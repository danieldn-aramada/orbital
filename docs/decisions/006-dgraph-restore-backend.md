# 006 — DGraph Restore Backend

## Context

Orbital restores DGraph from S3 backups using `dgraph live` — a CLI tool that reads
files from a local filesystem and streams them to DGraph Alpha via gRPC. The question
is: how does orbital invoke `dgraph live`?

Two backends exist behind the `RestoreBackend` interface:

- **`docker`** (default) — `docker exec` into the local alpha container. Used for local dev.
- **`k8s`** — must invoke `dgraph live` inside the Kubernetes cluster.

This document covers the K8s backend options.

---

## Option 1: K8s Job (idiomatic, requires RBAC)

When restore is triggered, orbital creates a K8s `batch/v1` Job. The Job downloads
the backup from S3 via a presigned URL (generated by orbital) and runs `dgraph live`.
Orbital watches the Job until completion, then deletes it.

**Flow:**
1. Orbital generates a presigned S3 URL for the backup (short TTL, ~10 min).
2. Orbital creates a Job with two containers sharing an `emptyDir`:
   - Init container: downloads from presigned URL to `emptyDir` using `curl`.
   - Main container: `dgraph/dgraph:v24.1.4` — runs `dgraph live`.
3. Orbital polls `jobs.batch/v1` status until `succeeded` or `failed`.
4. Orbital reads logs via `pods/log` for the restore record.
5. Job has `ttlSecondsAfterFinished: 3600` and `activeDeadlineSeconds` matching
   `ORBITAL_RESTORE_TIMEOUT`.

**RBAC required:**
```yaml
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["create", "get", "list", "delete"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
```

**What this eliminates:**
- The `dgraph-live` bare Pod manifest and its `sleep infinity` container.
- The `orbital-restore-pvc.yaml` shared PVC.
- The pod affinity constraint (PVC colocation no longer needed).
- 24/7 idle resource consumption (256Mi–2Gi RAM).

**Why `jobs/create` is less privileged than `pods/exec`:**

`pods/exec` grants arbitrary code execution inside any running pod matching the label
selector — there is no guardrail on what command is run. Pod Security Admission cannot
restrict exec. CIS Kubernetes Benchmark 5.1.3 and AKS built-in policies flag it as a
lateral movement vector.

`jobs/create` allows creating new pods whose specs are subject to Pod Security
Admission (blocking host mounts, privileged containers, etc.). The Jobs are visible,
auditable, and scoped to what PSA allows. This is a normal privilege for an application
that orchestrates work.

**Tradeoffs:**
- Still requires RBAC — a cluster admin must create the RoleBinding once.
- Job creation/watch adds ~5–15s overhead (pod scheduling).
- Presigned URL TTL must exceed Job scheduling time.

---

## Option 2: Embedded binary (no RBAC required)

Orbital's Docker image includes the `dgraph` binary (copied from the official DGraph
image in a multi-stage build). Orbital runs `dgraph live` directly as a subprocess.

Orbital already has:
- The backup data (downloaded from S3 to a local temp dir).
- The Alpha gRPC address (`ORBITAL_DGRAPH_ALPHA_GRPC`).
- The Zero gRPC address (`ORBITAL_DGRAPH_ZERO_GRPC`).
- Network access to both within the cluster.

**Flow:**
1. Orbital downloads backup from S3 to a temp directory.
2. Orbital runs `dgraph live --files /tmp/.../data.json.gz --schema /tmp/.../schema.gz
   --alpha <grpc> --zero <zero-grpc>` via `exec.Command`.
3. Orbital streams stdout/stderr to the restore job log.
4. Temp directory cleaned up after completion.

No K8s API calls. No idle pods. No shared PVCs. No RBAC.

**Dockerfile change (multi-stage):**
```dockerfile
FROM dgraph/dgraph:v24.1.4 AS dgraph
FROM <orbital-base>
COPY --from=dgraph /usr/local/bin/dgraph /usr/local/bin/dgraph
```

**Tradeoffs:**
- Adds the `dgraph` binary to the orbital image (~100–200 MB). Must be kept in sync
  with the DGraph Alpha version deployed (`ORBITAL_DGRAPH_ALPHA_GRPC` target).
- `dgraph live` runs inside the orbital pod — CPU and memory pressure from a large
  restore affects the orbital server process. Mitigation: `runtime.GOMAXPROCS` or
  `cgroups` isolation, or just accept it (restore is rare, admin-only).
- Version skew: if orbital image is deployed with dgraph binary X but Alpha is
  upgraded to Y, restore may fail. Keep versions pinned together in kustomization.

**Why this is valid:**

`dgraph live` is purely a gRPC client — it has no special locality requirement. It does
not need to run inside the Alpha pod or any specific pod. It can run anywhere with
network access to Alpha and Zero gRPC ports, which orbital already has.

This is analogous to how database clients (psql, mysqldump) are commonly included in
application images for maintenance operations.

---

## Comparison

| | Option 1: K8s Job | Option 2: Embedded binary |
|---|---|---|
| RBAC required | `jobs/create`, `jobs/get`, `jobs/delete`, `pods/log` | None |
| K8s API calls | Yes (Job lifecycle) | None |
| Idle resource cost | None (ephemeral Job) | None |
| Restore pod pressure | Isolated Job pod | Runs inside orbital pod |
| Binary version sync | Job uses dgraph image directly | Must pin in Dockerfile |
| Works in Docker dev | No (K8s-only) | Yes (same code path) |
| Image size | No change | +100–200 MB |
| Auditability | K8s events + Job history | orbital logs only |

---

## Decision

**Option 2 (embedded binary) implemented.**

`ORBITAL_RESTORE_BACKEND` and `ORBITAL_DGRAPH_CONTAINER` env vars removed.
`DockerRestoreBackend` and `K8sRestoreBackend` replaced by `SubprocessRestoreBackend`.
The dgraph binary is copied from `dgraph/dgraph:v24.1.4` in the Dockerfile multi-stage build.

Removed from deployment:
- `dgraph-live` idle pod manifest
- `orbital-restore-pvc` shared PVC
- `rbac.yaml` Role + RoleBinding
- Restore volume mount from orbital Deployment

`RestoreBackend` interface retained for testability (mock in integration tests).
